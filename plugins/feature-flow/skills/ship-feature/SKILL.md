# ship-feature

기능 하나를 **계획 → 구현 → 리뷰 → 머지** 까지 같은 순서로 진행한다.
`$ARGUMENTS` 가 있으면 그것이 이번 기능이다. 없으면 대화에서 사용자가 말한 다음 기능을 쓴다.

이 스킬을 호출했다는 것 자체가 아래 git · gh 작업에 대한 사용자 지시다.
단, `main`(배포 브랜치) 머지는 **절대 하지 않는다.**

## 0. 시작 전에 정하는 것

### 프로젝트 규칙이 이긴다

프로젝트 `CLAUDE.md` · `AGENTS.md` 를 먼저 읽는다. 프로젝트에 같은 주제의 규칙이 있으면 이 스킬보다 프로젝트 규칙을 따른다.
프로젝트 `CLAUDE.md` 에 `## 작업 흐름 설정` 이 있으면 그 값을 쓰고, 없으면 아래 기본값을 쓴다.

```markdown
## 작업 흐름 설정

- 통합 브랜치: develop
- 배포 브랜치: main
- 계획서 위치: docs/plans
- 검증: npx tsc --noEmit · npx eslint <바꾼 파일>
- develop 머지: 자동        # 자동 | 사람
```

| 항목 | 기본값 |
| --- | --- |
| 통합 브랜치 | `develop` 이 원격에 있으면 `develop`, 없으면 저장소 기본 브랜치 (이때 11단계는 건너뛴다) |
| 배포 브랜치 | 저장소 기본 브랜치 (`gh repo view --json defaultBranchRef`) |
| 계획서 위치 | `docs/plans` |
| 검증 | 아래 "검증 명령 고르기" |
| develop 머지 | 저장소 소유자가 지금 `gh` 로그인 계정이면 `자동`, 조직 · 다른 사람 저장소면 `사람` |

`develop 머지: 사람` 이면 9단계(확인 리뷰)까지 하고 멈춰 보고한다. 머지는 사람이 한다.

### 검증 명령 고르기

무거운 전체 빌드(`next build`, `vite build`, `gradlew build` 등)는 쓰지 않는다. 한 프로세스짜리 검사만 쓴다.

| 프로젝트 | 검증 |
| --- | --- |
| `tsconfig.json` 있음 | `npx tsc --noEmit` |
| eslint 설정 있음 | `npx eslint <바꾼 파일만>` |
| vitest · jest | 바꾼 기능의 테스트 파일만, 워커 1개 (`--maxWorkers=1` / `--runInBand`) |
| 그 밖 | 프로젝트 `CLAUDE.md` 에 적힌 명령. 없으면 사용자에게 묻는다 |

검사는 한 번에 하나씩 돌린다(`&&` 로 묶지 않는다). 통과한 뒤 코드가 안 바뀐 검사는 다시 돌리지 않는다.

### 사전 확인

```bash
git status -sb                  # 커밋 안 된 변경이 있으면 멈추고 묻는다 (남의 작업일 수 있다)
gh auth status
codex --version                 # 실패하면 리뷰를 건너뛰지 말고 멈춰서 보고한다
```

## 1. 브랜치

```bash
git switch <통합> && git pull && git switch -c feature/<기능-이름>
```

버그 수정이면 `fix/<내용>`. 이름은 kebab-case 영어.

## 2. 계획서 · 체크리스트 (코드보다 먼저)

`<계획서 위치>/YYYY-MM-DD-<기능-이름>/plan.md`, `checklist.md` 를 만든다.
형식은 이 스킬 폴더의 [templates/plan.md](templates/plan.md) · [templates/checklist.md](templates/checklist.md) 를 따른다.

- 기존 코드를 먼저 읽고, 재사용할 공용 컴포넌트 · 함수를 계획서 "설계" 에 적는다.
- 체크리스트 항목 하나 = 커밋 하나로 끝낼 수 있는 크기.
- 계획서는 저장소에 올라간다. 비밀값 · 이메일 · 개인 신상 · 고객 데이터는 옮기지 않고 `<비밀값>` 처럼 가린다.
- 이 두 파일을 브랜치 첫 커밋으로 올린다: `docs(plan): <기능> 계획서 · 체크리스트`
- 사용자가 "계획 먼저 보여줘" 라고 했으면 여기서 멈추고 보고한다. 아니면 확인을 기다리지 않고 구현한다.

## 3. 구현

체크리스트 순서대로 구현한다. 항목을 끝낼 때마다 `[x]` 로 바꾸고, 그 항목의 코드 커밋에 체크리스트 변경을 같이 담는다.
하다가 계획이 바뀌면 plan.md 를 고치고, checklist.md 에 항목을 더하거나 `~~취소~~` 로 남긴다 (지우지 않는다).

## 4. 성격별 커밋

- `feat` / `fix` / `style` / `refactor` / `chore` / `docs` 로 나눈다. 한 파일이 두 작업에 걸치면 부분 스테이징으로 가른다.
- **각 커밋이 그 자체로 검증을 통과하는 순서**로 놓는다. DB 마이그레이션은 그 기능 커밋에 같이 넣는다.
- 메시지: `type(scope): 한 줄 요약` + 본문에 왜 그렇게 했는지와 근거 수치.
- 메시지는 파일로 써서 `git commit -F <파일>` 로 넘긴다 (PowerShell 은 큰따옴표가 든 인자를 쪼갠다). 파일은 BOM 없는 UTF-8.

## 5. 최신 통합 브랜치 반영 · PR

```bash
git fetch origin && git merge origin/<통합>    # 충돌을 풀었으면 검증을 다시 돌린다
git push -u origin feature/<기능-이름>
gh pr create --base <통합> --title "<type>: <요약>" --body-file <저장소 밖 임시 파일>
```

- 이미 push 한 이력을 바꾸지 않도록 rebase 대신 merge.
- PR 본문에 계획서 · 체크리스트 경로와 사람이 확인할 테스트 체크리스트를 적는다. **아직 머지하지 않는다.**

## 6. 전수 리뷰 (1번)

PR 전체(`git diff origin/<통합>...HEAD`, 커밋 전부 합친 변경)를 한 번에 본다.
**Codex 와 Claude 리뷰어(Agent)를 동시에 따로** 돌려 서로 놓친 것을 잡게 한다. 지시문은 [review-prompt.md](review-prompt.md).

```bash
# 지시문을 저장소 밖 임시 파일에 쓰고, 마지막 인자 `-` 로 표준 입력에서 읽게 한다.
codex exec -s read-only --ephemeral -c model_reasoning_effort="high" \
  -o <저장소 밖 임시 폴더>/codex-review-pr<번호>-r1.md - < <임시 폴더>/review-prompt.txt
```

- 지시문을 `"$(cat 파일)"` 처럼 인자로 넘기지 않는다. Windows 는 지시문 안의 큰따옴표에서 인자를 잘라 Codex 가 첫 줄만 받는다.
- 표준 입력을 열어 두면 "Reading additional input from stdin" 에서 멈춘다. `- < 파일` 이 지시문을 넘기면서 입력도 닫는다.
- `codex review --base` 는 지시문과 함께 못 쓴다(`--base` 와 PROMPT 가 배타적). `codex exec` 를 쓴다.
- 오래 걸리므로 백그라운드로 돌리고, 그동안 Claude 리뷰어 Agent(`general-purpose`, 읽기 전용 지시)를 띄운다.
- 결과 파일은 **저장소 밖**(세션 임시 폴더)에만 만든다.

두 결과를 합치고 중복을 뺀 뒤, **지적마다 코드를 직접 열어** 맞음 / 틀림 / 일부 맞음을 판단한다. 리뷰어 말을 그대로 믿지 않는다.

## 7. GitHub PR 리뷰로 게시 (회차당 1건)

일반 코멘트가 아니라 PR Review 로 남긴다. 같은 계정이면 Approve · Request changes 를 못 하므로 `event: COMMENT`.

- 본문 첫 줄: `🤖 리뷰 <회차>차 (<실제로 돌린 리뷰어>) · 범위 <통합>...<HEAD 짧은 해시> (커밋 n개 · 파일 n개 전체)`
- 본문에 판단 표 `| 출처 | 지적 | 판단 | 처리 |`, 원문은 `<details>` 로 접는다.
- 파일:줄이 있는 지적은 인라인 코멘트로. diff 에 없는 줄은 본문 표에만.

JSON 을 저장소 밖 임시 폴더에 쓰고 넘긴다:

```bash
gh api repos/<owner>/<repo>/pulls/<번호>/reviews --input <임시 폴더>/review-pr<번호>-r<회차>.json
```

```json
{"commit_id": "<HEAD 전체 해시>", "event": "COMMENT", "body": "<판단 표>",
 "comments": [{"path": "src/a.ts", "line": 44, "side": "RIGHT", "body": "<지적 · 판단>"}]}
```

`side` 는 추가 · 그대로인 줄이면 `RIGHT`, 지운 줄이면 `LEFT`. 올리기 전에 "민감 정보 검사" 를 거친다.

## 8. 한 번에 고친다 (같은 기능 브랜치)

- 맞는 "꼭 고칠 것" · "고치면 좋은 것" 은 모두 고친다. "사소함" 은 판단해서 고치고, 안 고치면 이유를 표에 적는다.
- 틀린 지적은 고치지 않고 이유를 표에 적는다.
- 지적을 고치는 데 필요한 만큼만 바꾼다 (새 지적거리를 만들지 않는다).
- 성격별로 커밋하고 본문에 어떤 지적을 고쳤는지 적는다. 체크리스트 "리뷰" 칸에 결과를 적고 push.

## 9. 확인 리뷰 (1번)

Codex 로 한 번 더 보되 범위를 **"6 의 지적이 제대로 고쳐졌는지 · 고치면서 새로 깨진 것이 있는지"** 로 좁힌다. 새 개선 제안은 받지 않는다.
결과는 7 과 같은 형식(2차, 리뷰어 `Codex`)으로 게시한다.

- 맞는 "꼭 고칠 것" 은 고친다. "고치면 좋은 것" · "사소함" 은 몇 줄로 끝나는 것만 고치고 나머지는 PR 에 이유를 적고 넘긴다.
- 이 수정 뒤에는 리뷰를 다시 돌리지 않는다. **PR 하나당 전수 1번 + 확인 1번.** 3번째가 필요하면 멈추고 사람에게 묻는다.

### 리뷰 요약 코멘트 (머지 직전 1건)

PR Review 는 Conversation 탭에서 커밋 사이에 끼고, 고친 줄의 인라인 지적은 **Outdated** 로 접혀 잘 안 보인다.
확인 리뷰 수정까지 push 한 뒤, 머지 직전에 PR 맨 아래에 일반 코멘트로 요약을 **딱 1건** 단다 (`gh pr comment <번호> --body-file <임시 파일>`).

```markdown
## 🤖 리뷰 요약

| 회차 | 리뷰어 | 범위 | 지적 | 처리 |
|---|---|---|---|---|
| [1차 전수](<리뷰 링크 #pullrequestreview-<id>>) | Codex + Claude | <통합>...<해시> | 꼭 n · 좋음 n · 사소 n | 맞음 n → 반영 / 안 고침 n |
| [2차 확인](<리뷰 링크>) | Codex | <해시>..<해시> | ... | ... |

- 머지 판단과 다음 작업으로 넘긴 것
```

리뷰 id 는 `gh api repos/<owner>/<repo>/pulls/<번호>/reviews --jq '.[] | [.id, .body[:20]]'` 로 얻는다. 올리기 전에 민감 정보 검사.

## 10. 통합 브랜치 머지 (`develop 머지: 자동` 일 때만)

확인 리뷰에서 맞는 "꼭 고칠 것" 이 남지 않았으면 머지한다.

```bash
git fetch origin && git merge-base --is-ancestor origin/<통합> HEAD; echo $?
```

- `0`: 그대로 머지.
- `1`: 그 사이 통합 브랜치가 바뀌었다. `git merge origin/<통합>` 후 검증을 다시 돌린다. 충돌 없이 통과하면 리뷰 없이 머지한다 (들어온 변경은 자기 PR 에서 리뷰를 거쳤다). 충돌을 손으로 풀었으면 멈추고 사람에게 묻는다.
- `2` 이상: git 오류. 멈추고 보고한다.

```bash
gh pr merge <번호> --merge --delete-branch     # 나눈 커밋을 그대로 남기려고 merge commit 방식
```

머지 뒤에는 기능 브랜치에 커밋할 수 없으니, 체크리스트의 남은 두 칸은 PR 머지 기록과 develop→main PR 로 대신한다.

## 11. develop → main PR

열린 `<통합>` → `<배포>` PR 이 없으면 만들고(`release: develop → main`), 있으면 본문의 포함 기능 목록만 갱신한다.

## 12. 멈추고 보고

`main` 머지는 사람이 한다. 보고에 넣을 것:
- PR 링크, 리뷰 회차별 지적 수와 처리 결과
- 사람이 해야 할 일 (DB 마이그레이션 반영, 환경변수 등)
- **화면 테스트 체크리스트** (어디를 누르면 → 무엇이 보여야 하는지)
- 코드 분리 점검 결과 (공통화한 것, 새로 만든 공용 코드)

## 외부에 올리기 전 민감 정보 검사

PR 본문 · 리뷰 · 커밋 메시지 · 계획서는 공개될 수 있다. 올리기 전에 검사하고, 걸리면 `<가림>` 으로 바꾼다.

```bash
grep -nE 'sb_secret_|sb_publishable_|sbp_|gh[pousr]_[A-Za-z0-9]|eyJhbGci|sk-[A-Za-z0-9]|AKIA[0-9A-Z]{16}|[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}|01[016789]-?[0-9]{3,4}-?[0-9]{4}' <파일>
```

- Supabase · GitHub · JWT · OpenAI · AWS 키, 이메일, 휴대전화 번호를 잡는다. 커밋 작성자 · Co-Authored-By 의 noreply 주소는 예외.
- 패턴에 안 걸리는 비밀번호 · 주소 · 고객 데이터는 직접 읽고 확인한다. 의심스러우면 올리지 않고 묻는다.

## 함정

| 증상 | 원인 · 대처 |
| --- | --- |
| Codex 가 10분 넘게 출력 없음 | stdin 대기. 지시문을 `- < 파일` 로 넘기지 않았다 |
| Codex 가 "지적 사항을 보내 주세요" 같은 답만 함 | 지시문이 첫 줄에서 잘렸다 (Windows 인자 따옴표). `- < 파일` 로 넘긴다 |
| 커밋 메시지가 여러 인자로 쪼개짐 | PowerShell 따옴표. `git commit -F <파일>` |
| 커밋 메시지 맨 앞에 깨진 문자 | BOM. Bash heredoc 이나 BOM 없는 UTF-8 로 쓴다 |
| 리뷰가 커밋별로 달린 것처럼 보임 | 일반 코멘트를 썼다. PR Review 로 한 건에 모은다 |
| PR 에서 리뷰가 안 보이고 커밋만 보임 | 리뷰가 커밋 사이에 끼고 인라인은 Outdated 로 접힌다. 머지 직전 요약 코멘트를 단다 |
| 인라인 코멘트 422 오류 | 그 줄이 diff 에 없다. 본문 표로 옮긴다 |
