# 계획 먼저 (선택)

SKILL.md 의 기본은 「바로 하기」다. 아래 경우에만 이 문서대로 계획서를 먼저 쓰고 사용자 승인을 받은 뒤 구현한다.

- 사용자가 "계획 먼저 보여줘" · "설계부터" 처럼 계획을 요청했다.
- DB 테이블을 2개 이상 바꾸는 큰 기능이다 (마이그레이션 순서 · 데이터 옮기기를 미리 맞춰야 한다).

구현 · 커밋 · PR · 리뷰는 계획서가 생긴 뒤에도 SKILL.md 「바로 하기」 흐름 그대로다. 계획서는 승인과 이어하기를 위한 기록일 뿐, 체크리스트 항목마다 커밋하거나 검사하지 않는다.

## 1. 현황 파악

| 상황 | 할 일 |
| --- | --- |
| 소스 코드가 거의 없는 새 프로젝트 | [setup.md](setup.md) "기반 작업" 을 먼저 한다 |
| 설정 파일(`<저장소>/.claude/han-pipeline.md`) 없음 | [setup.md](setup.md) "설정 파일 만들기" |

- 사용자가 준 문서(요구사항 · DB 설계 · API 명세 · 시안)가 기준이다. 계획서는 그 문서의 항목을 가리키기만 하고 원본은 고치지 않는다.
- 문서에 없는 것은 계획서 "결정 사항 — 에이전트가 정함" 에 기본안으로 적는다.
- 질문은 한 번에 — 문서끼리 · 문서와 코드가 부딪히는 점, 문서만으로 정할 수 없어 막히는 점만 AskUserQuestion 한 번(최대 4개)으로.

## 2. 구조 설계

`han-pipeline:explorer` 로 재사용할 공용 코드 · 비슷한 기존 기능 · 커질 위험이 있는 파일을 찾고(같은 영역의 최근 계획서가 있으면 그것을 읽고 바뀐 곳만 확인), 계획서 "구조 설계" 네 칸을 채운다: **재사용할 기존 코드 / 새로 만들 공용 코드 / 파일 배치 / 커질 위험과 나눌 방법**. 해당 없음이면 "없음 — <이유>".

## 3. 계획서

`<계획서 위치>/YYYY-MM-DD-<작업-이름>/plan.md` 하나. 형식은 프로젝트 규칙, 없으면 [templates/plan.md](templates/plan.md).

- 이번에 하는 것 · 하지 않는 것, 구조 설계, DB 변경 순서, 테스트 계획(무엇을 단위 · 화면 · 사람이 확인하는지), 체크리스트(기능 단위 — 커밋 하나에 들어갈 크기).
- 비밀값 · 이메일 · 개인 신상은 `<비밀값>` 처럼 가린다.
- 파일만 쓰고 `han.mjs stop` 한 뒤 승인을 기다린다. 승인 뒤 SKILL.md 「바로 하기」 3 단계부터 잇는다. git 모드면 계획서를 브랜치의 첫 커밋으로 올린다.

## 이어하기

"이어서 해줘" 면 계획서 위치에서 체크리스트에 `- [ ]` 가 남은 최근 계획서를 고르고(둘 이상이면 묻는다), 체크리스트 머리의 브랜치로 옮겨 `git log` · `git diff` 로 어디까지 됐는지 맞춘 뒤 잇는다.
