# 여러 기능을 한 번에 (worktree 병렬)

한 요청에 서로 다른 기능이 둘 이상 있을 때(예: "할 일 달력이랑 담당자 기능 올려줘", 목록으로 여러 개) 기능마다 작업 폴더(git worktree)와 브랜치를 따로 만들고, 폴더마다 Claude 하나가 그 기능을 끝까지 맡게 한다.
**Orca 가 켜져 있으면 그 작업 폴더의 Orca 작업공간에 Claude 를 띄운다** — 사용자가 기능마다 진행을 화면에서 보고 중간에 답할 수 있다. Orca 가 없으면 이 세션 안의 하위 에이전트가 맡는다(지금까지의 방식).
이 세션은 **지휘자**다. 기능을 나누고, 하위 에이전트를 띄우고, 끝난 PR 을 하나씩 통합 브랜치에 머지한다.
`han.mjs` 는 SKILL.md 첫머리의 스크립트 경로다. 명령은 Git Bash 에서 실행한다.

- **git 모드에서만** 한다. worktree 는 브랜치를 만드는 git 작업이라, 로컬 모드에서는 기능을 하나씩 차례로 하고 보고에 "'올려줘' 로 부르면 동시에 진행합니다" 라고 적는다.
- 기능이 하나면 이 문서를 쓰지 않는다 (SKILL.md 흐름 그대로).
- 동시에 빨라지는 것은 생각 · 코드 쓰기 · 리뷰 대기다. 무거운 일(타입 검사 · 린트 · 테스트 · Codex)은 `han.mjs check` · `run` 이 **PC 전체에서 한 번에 하나**만 돌게 줄을 세운다. 하위 에이전트는 이 세션 안에서 돌아 메모리를 거의 더 쓰지 않는다.

## 1. 나누기 · 겹침 판단

1. 기능마다 `han-pipeline:explorer` 를 부른다 (한 메시지에 동시에). 작업 설명과 함께 **고칠 파일 · 새로 만들 파일 · DB 변경(테이블)** 예상 목록을 달라고 한다.
2. 표로 정리한다: `| 기능 | 고칠 파일 | 새 파일 | DB 테이블 |`.
3. 아래 중 하나라도 겹치는 기능끼리는 **같은 줄**로 묶어 차례로 한다 (나중에 통합 브랜치에 머지할 때 충돌이 나기 때문이다).
   - 같은 파일을 고친다 (공용 컴포넌트, 같은 화면 page, 같은 타입 · 조회 파일, 라우트 · 설정 파일).
   - 같은 DB 테이블을 바꾼다.
   - 패키지를 설치하거나 `package.json` · 잠금 파일을 바꾼다 → 그 기능은 **혼자 한 줄**, 다른 줄이 모두 끝난 뒤에 한다 (작업 폴더들이 원래 폴더의 `node_modules` 를 같이 쓴다).
4. 줄 수는 설정의 `동시 기능 수`(기본 3)까지. 넘으면 나머지 줄은 앞 줄이 끝난 뒤에 시작한다.
5. 크기 "큼" 인 기능은 SKILL.md 3 단계대로 계획서 승인을 먼저 받는다 (그 기능만 기다리고 나머지는 진행).
6. 표와 줄 나눔을 사용자에게 한 번 보여 주고 바로 시작한다 (사용자가 "계획 먼저 보여줘" 라고 했을 때만 멈춘다).

## 2. 작업 폴더 만들기

줄마다 첫 기능의 작업 폴더를 만든다.

```bash
han.mjs worktree add <기능-이름> [--branch <브랜치 이름>] --launch --prompt-file <지시문 파일>
# 버그면 --fix (fix/<이름>), 기준을 바꾸려면 --base <브랜치>
```

- `--branch`: 프로젝트 규칙의 브랜치 이름(예: `feat/<짧은 이름>`). 주지 않으면 `feature/<기능-이름>`.
- `--launch --prompt-file`: 3 단계 지시문을 저장소 밖 임시 파일에 먼저 쓰고 넘긴다. 작업 폴더를 만든 뒤 Orca 에 Claude 를 띄우고 결과를 `launch:` 한 줄로 남긴다 — `launch: orca` 면 띄웠다, `launch: fallback` 이면 못 띄웠다(Orca 없음 · 꺼짐 · 실패), `launch: unknown` 이면 응답을 못 받았다(Orca 화면에서 그 작업공간을 확인하고, 다시 띄우지 않는다).

- 저장소 옆 `<저장소>.worktrees/<기능-이름>` 에 최신 통합 브랜치에서 딴 `feature/<기능-이름>` 브랜치로 만든다. 저장소 안이 아니라서 다른 기능의 타입 검사 · 린트에 섞이지 않는다.
- `node_modules` 는 원래 폴더 것을 연결한다. 설정의 `워크트리 준비` 명령(Next.js 면 `npx next typegen`)을 한 번 돌린다.
- `.env.local` 같은 무시 파일은 따라오지 않는다. 검사(타입 · 린트 · 단위 테스트)에는 필요 없다. 필요한 기능이면 그 기능만 병렬에서 빼고 원래 폴더에서 한다.

## 3. 기능마다 Claude 띄우기

지시문을 먼저 쓴다(아래 틀). 2 단계 `--launch --prompt-file` 로 넘기면 Orca 작업공간에 뜬다.

- `launch: orca` — 그 작업공간의 Claude 가 끝까지 한다. 이 세션은 그 세션이 보내는 결과 메시지를 기다린다. 사용자가 그 작업공간에서 직접 지시해도 된다.
- `launch: unknown` — 띄웠는지 모른다(응답 유실 · 시간 초과). 하위 에이전트로 다시 띄우지 않는다. 사용자에게 Orca 화면에서 그 작업공간을 확인해 달라고 하고, Claude 가 떠 있으면 `orca` 와 같이 기다린다.
- `launch: fallback` — 지시문을 그대로 이 세션의 하위 에이전트로 띄운다. 줄마다 하나씩, **한 메시지에 여러 Agent 호출**로 동시에 (`subagent_type: general-purpose`, `run_in_background: true`).

지시문 (`<지휘 세션 이름>` 은 ListAgents 의 "This session is …" 이름):

```
han-pipeline 의 병렬 하위 작업이다. Skill han-pipeline:han-pipeline 을 불러 parallel.md "하위 작업 규칙" 을 따른다.
- 작업: <기능 설명 — 사용자 원문 그대로 포함>
- 작업 폴더: <작업 폴더 절대 경로> · 브랜치 <브랜치> (이미 만들어 둠)
- 원래 저장소 폴더: <원래 폴더> — 읽기만 한다. 파일을 고치거나 명령을 돌리지 않는다.
- 맡지 않는 파일 (다른 기능이 고침): <목록>. 꼭 고쳐야 하면 고치지 말고 멈춰 이유를 돌려준다.
- 구조 설계 메모: <explorer 결과 요지>
- 프로젝트 규칙: <원래 폴더>/CLAUDE.md · AGENTS.md 를 먼저 읽는다.
- 끝: 확인 리뷰 · 리뷰 요약 코멘트까지. 통합 브랜치 머지 · 통합→배포 PR 은 하지 않는다.
- 돌려줄 것: PR 번호 · 링크, CI 결과, 리뷰 회차별 지적 수와 처리, 사람 확인 체크리스트, 남은 일 · 막힌 점.
- (Orca 로 떴으면) 끝나면 위 내용을 SendMessage 로 지휘 세션 <지휘 세션 이름> 에 보낸다.
```

띄운 뒤 사용자에게 표로 알린다: `| 기능 | 브랜치 | 작업 폴더 | 상태 |`. 진행 중에는 기다리고, 하위 결과가 오는 대로 4 단계를 한다.

## 하위 작업 규칙 (하위 에이전트가 따른다)

SKILL.md 흐름(구조 설계 → 계획 → 테스트 먼저 구현 → 검사 → 리뷰)을 그대로 하되 아래가 다르다.

- **모든 Bash 명령을 `cd "<작업 폴더>" && …` 로 시작한다.** 파일은 작업 폴더 아래 절대 경로로만 읽고 쓴다. 원래 폴더의 파일을 고치지 않는다.
- 시작: `cd "<작업 폴더>" && han.mjs start`. 브랜치는 이미 있으므로 [git-flow.md](git-flow.md) 1 단계(브랜치 따기)를 건너뛰고 계획서 · 체크리스트 첫 커밋부터 한다.
- **브랜치를 바꾸지 않는다** (`git switch` · `checkout` 금지). 통합 브랜치는 원래 폴더가 쓰고 있어 작업 폴더에서 꺼낼 수 없다. 최신 반영은 `git fetch origin && git merge origin/<통합>`.
- **이 세션 안의 하위 에이전트면 사용자에게 묻지 않는다** (AskUserQuestion 금지 — 화면에 안 보인다). 정할 수 없는 것은 계획서 "결정 사항 — 에이전트가 정함" 에 기본안으로 적고 간다. 진행이 막히면 멈추고 이유를 돌려준다.
  **Orca 작업공간에 뜬 Claude 면 물어도 된다** — 사용자가 그 화면을 본다. 다만 질문은 SKILL.md 3 단계처럼 한 번에 모은다.
- 패키지를 설치하지 않는다 (`node_modules` 를 같이 쓴다). 설치가 필요하면 멈추고 돌려준다.
- DB 마이그레이션 파일 이름의 시각은 `cd "<작업 폴더>" && han.mjs stamp` 로 받는다 (파일마다 한 번). 여러 작업 폴더가 동시에 만들어도 순서가 겹치지 않는다.
- 화면 자동 테스트는 하지 않는다. dev 서버는 원래 폴더의 코드를 띄우고 있다. 화면 항목은 사람 확인 체크리스트로 넘긴다.
- 맡지 않는 파일 목록을 지킨다.
- 검사 · Codex 는 `han.mjs check` · `han.mjs run` 으로만 돌린다 (PC 전체 줄에 선다). 기다림 안내가 나와도 정상이다.
- PR 을 만든 뒤 **리뷰 전에 PR 검사(CI) 결과를 확인**한다. 실패면 먼저 고친다.
- 리뷰는 [git-flow.md](git-flow.md) 4~8 단계(전수 · 게시 · 수정 · 확인 · 요약 코멘트)까지. 9~10 단계(머지 · 통합→배포 PR)는 지휘자가 한다. 체크리스트의 그 두 칸은 비워 둔다.
- 끝나면 `cd "<작업 폴더>" && han.mjs stop` 하고 지시문의 "돌려줄 것" 을 돌려준다. Orca 로 떴으면 SendMessage 로 지휘 세션에 보낸다(지휘 세션 이름은 지시문에 있다).

## 4. 머지 (지휘자, 끝난 순서대로 하나씩)

하위 결과를 받으면 확인한다: 확인 리뷰에서 맞는 "꼭 고칠 것" 이 남지 않았고 CI 가 통과했는가. 아니면 그 기능은 머지하지 않고 보고에 남긴다.

```bash
cd "<작업 폴더>" && git fetch origin && git merge-base --is-ancestor origin/<통합> HEAD; echo $?
```

- `0`: 아래 머지로.
- `1`: 그 사이 다른 기능이 먼저 머지됐다. `cd "<작업 폴더>" && git merge origin/<통합>` → `han.mjs check` → push → CI 확인. 충돌 없이 통과하면 머지한다. **충돌을 손으로 풀었으면 멈추고 사람에게 묻는다** (리뷰 횟수 규칙).
- `2` 이상: git 오류. 멈추고 보고.

머지는 작업 폴더를 먼저 지운 뒤에 한다 (브랜치가 작업 폴더에 꺼내져 있으면 `--delete-branch` 가 로컬 브랜치를 못 지운다).

```bash
han.mjs worktree remove <기능-이름>                 # 바뀐 파일이 있으면 지우지 않는다 → 커밋 · push 를 확인
gh pr merge <번호> --merge --delete-branch           # 원래 폴더에서
```

- 같은 줄에 다음 기능이 있으면 그 기능의 작업 폴더를 새로 만들고(최신 통합 브랜치 기준) 3 단계로 띄운다.
- 모든 줄이 끝나면 통합→배포 PR 을 한 번에 갱신한다 ([git-flow.md](git-flow.md) 10 단계, 포함 기능 목록에 이번 PR 들).

## 5. 정리 · 이어하기

- 머지한 기능의 작업 폴더는 4 단계에서 지웠다. 머지하지 못한 기능(꼭 고칠 것 남음 · 충돌 · 막힘)은 작업 폴더를 남기고 보고에 경로와 이유를 적는다.
- 남은 작업 폴더 보기: `han.mjs worktree list`. 이어서 하려면 그 기능만 3 단계 지시문에 "이어하기" 를 더해 다시 띄운다 (`han.mjs start --resume` 으로 체크리스트를 이어 간다). 작업 폴더가 이미 있으면 `worktree add` 대신 `orca agent launch --agent claude --worktree path:<작업 폴더> --prompt "<지시문>" --focus` 로 그 작업공간에만 띄운다.
