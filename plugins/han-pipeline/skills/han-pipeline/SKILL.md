# han-pipeline

개발 요청 하나를 **이 세션에서 직접**, 한 번의 명령으로 끝까지 한다: **고치기 → 바꾼 파일 테스트 → 기능 단위 커밋 · push → PR 하나 → 리뷰 → 이슈 → 보고.**
`$ARGUMENTS` 가 있으면 그것이 이번 작업이다 (파일 경로면 그 파일을 읽는다). 없으면 대화에서 사용자가 말한 작업을 쓴다.

**목표 시간(추측)**: 작은 수정 15~30분, 화면 · 서버를 여럿 건드리는 큰 묶음 2시간 안팎. 이보다 크게 늘어지면 무엇에 막혔는지(검사 줄 서기 · 메모리 · 질문 대기) 사용자에게 한 줄로 알린다.

**스크립트**: `${CLAUDE_PLUGIN_ROOT}/scripts/han.mjs`. 셸 변수는 Bash 호출 사이에 남지 않으므로 호출마다 경로를 그대로 적는다. 아래 `han.mjs <명령>` 은 `node "${CLAUDE_PLUGIN_ROOT}/scripts/han.mjs" <명령>` 의 줄임이다. 경로가 치환되지 않았으면 `~/.claude/plugins/cache/*/han-pipeline/*/scripts/han.mjs` 를 찾아 쓴다.
**셸**: 명령 예시는 Git Bash(POSIX) 기준이다. Windows PowerShell 에는 `&&` · `\` 줄 이음 · `<` 입력 연결이 없다.

## 원칙

- **절차보다 결과.** 작업 크기와 상관없이 같은 절차를 다 밟지 않는다. 계획서 파일 · 구조 조사 에이전트 · 작업 세션 띄우기는 기본이 아니다 — 필요할 때만 ([plan-mode.md](plan-mode.md) · [parallel.md](parallel.md)).
- **사용자가 가져온 문서가 기준이다.** 요구사항 · DB 설계 · API 명세 · 시안을 받았으면 그대로 따른다.
- **고치기 전에 기존 코드를 먼저 본다.** 비슷한 기능 · 공용 부품이 있으면 가져다 쓰고, 프로젝트의 기존 스타일을 따른다. 두 곳 이상에서 쓸 것만 공용으로 뺀다.
- **검사는 가볍게, PR 전에 한 번 넓게.** 커밋 관문은 바꾼 파일의 테스트만(`han.mjs check` — 설정 "빠른 테스트"), PR 직전에만 관련 테스트까지(`han.mjs check --full`). 훅이 검사를 통과하지 않은 커밋 · PR 생성을 막는다.
- **사용자가 다른 작업을 계속할 수 있게 돈다.** 무거운 일은 한 번에 하나, `start` 의 자원 예산을 지킨다.
- **사람만 하는 일은 하지 않는다.** 배포 브랜치 머지 · push, force push, DB 적용 · 직접 쿼리, 운영 배포 · 환경변수 · 비밀값 변경, 원격 저장소 생성. 실행할 명령을 적어 보여 주고 멈춘다. 훅도 막는다.
- **통합 · 배포 브랜치에서는 커밋하지 않는다.** 작은 수정도 브랜치(작업 폴더)를 따서 PR 로 올린다.
- **기능 하나 = PR 하나.** 서버 · 관리자 · 화면을 한 브랜치에서 끝까지 만들고 PR 하나에 리뷰 · 요약 · 이슈를 한 번에 한다. 커밋 · push 는 기능 단위(검사가 통과하는 덩어리)마다 — 세션이 끊겨도 작업이 남게.
- **프로젝트 규칙이 이긴다.** 프로젝트 `CLAUDE.md` · `AGENTS.md` 를 먼저 읽는다. 같은 주제(브랜치 · 커밋 · 리뷰 횟수 · 머지 · 이슈)의 규칙이 있으면 그것을 따른다.

## 1. 모드 고르기

| 모드 | 언제 | git · gh |
| --- | --- | --- |
| **git 모드** | 이번 요청에 git 흐름을 맡기는 말이 있다: "올려줘", "PR", "머지까지", "브랜치로", 또는 프로젝트 규칙이 git 흐름의 시작 문구로 적어 둔 말과 같은 뜻 | 브랜치 · 커밋 · push · PR · 리뷰 게시 · 이슈까지 한다 |
| **로컬 모드** | 그 밖 ("만들어줘", "고쳐줘"). 이번 요청에 git 을 맡기는 말이 없으면 로컬 모드다 | git 상태를 바꾸는 명령과 gh 쓰기를 하지 않는다. 끝까지 고치고 테스트한 뒤 커밋 나눔안과 명령을 보여 주고 멈춘다 |

- **계획 먼저**: 사용자가 계획을 먼저 보자고 했거나 DB 테이블 2개 이상을 바꾸는 큰 기능이면 [plan-mode.md](plan-mode.md) 로 계획서 승인을 받은 뒤 아래 흐름으로 돌아온다.
- **여러 기능 동시에**: 사용자가 동시에 하라고 **분명히 요청했고** `start` 가 보인 남은 메모리가 넉넉할 때만 [parallel.md](parallel.md). 아니면 기능 하나씩 차례로 이 세션에서 한다 — 작업 세션 하나가 메모리를 크게 쓰고, 새로 띄운 세션은 규칙 · 코드를 처음부터 다시 읽는다.
- **병렬 하위 작업으로 불렸으면** (지시문이 "han-pipeline 의 병렬 하위 작업이다" 로 시작): [parallel.md](parallel.md) "하위 작업 규칙" 이 우선한다.

## 2. 시작

```bash
git status -sb
han.mjs start
```

`start` 는 실행 표시를 켜고 설정 · 자원 예산 · **시작 전부터 바뀌어 있던 파일** 목록을 보여 준다. 그 파일들은 남의 작업일 수 있으므로 건드리지 않는다 (검사에서도 빠진다). 설정 파일이 없으면 [setup.md](setup.md) "설정 파일 만들기".

git 모드면 작업 폴더를 따서 그 폴더에서 일한다 (원래 폴더의 브랜치는 바꾸지 않는다):

```bash
han.mjs worktree add <작업-이름> [--fix]      # 앱별 node_modules 연결 · 설정 "작업 폴더 복사" 파일 복사까지
```

**자원 예산** — 무거운 일(타입 검사 · 린트 · 테스트 · 브라우저 · 패키지 설치)은 **한 번에 하나**. 검사는 `check`, 그 밖의 무거운 명령은 `han.mjs run "<명령 전체>"` (남은 메모리 확인 · 낮은 우선순위 · PC 전체 줄 서기). 전체 빌드 · 전체 테스트 · dev 서버 새로 켜기는 하지 않는다. 통과한 뒤 파일이 안 바뀐 검사는 다시 돌리지 않는다.

## 3. 파악 · 질문 한 번

- 고칠 곳과 비슷한 기존 기능 · 공용 부품을 Grep · Read 로 직접 찾는다 (구조 조사 에이전트는 부르지 않는다).
- **앞뒤 기능 잇기** — 이번에 만들거나 바꾸는 데이터를 **읽는** 다른 화면 · API, 이번 기능이 읽는 데이터를 **다른 길로도** 만드는 기능(관리자 처리 · 일괄 처리)을 찾는다. 같이 고쳐야 하면 이번 범위에 넣고, 아니면 PR 본문 「이번에 하지 않은 것」에 적는다.
- 질문은 여기서 한 번에 — 문서끼리 · 문서와 코드가 부딪히는 점, 문서만으로 정할 수 없어 막히는 점만 AskUserQuestion 한 번(최대 4개). 그 밖에는 기본안으로 가고 PR 본문 「결정 사항」에 ⚠️ 로 적는다.

## 4. 고치기 (기능 단위로 반복)

1. 고친다. 테스트도 같이 쓴다 — 새 동작 · 실패 경로(불러오기 실패 · 거절 · 빈 목록)의 테스트, 버그면 재현 테스트를 먼저 ([testing.md](testing.md)).
2. **바꾼 파일의 테스트만** 돌린다 — `han.mjs run "<테스트 명령> <바꾼 테스트 파일들>"` (워커 하나). 통과할 때까지 고친다.
3. 기능 하나(검사가 통과하는 덩어리)가 끝나면 `han.mjs check` → 커밋 → push ([git-flow.md](git-flow.md) 2 단계). 로컬 모드면 커밋 대신 다음 기능으로.
4. 바꾼 동작은 사람이 화면에서 볼 확인 줄로 모아 둔다 — PR 본문 「직접 확인할 것」 표(`| 이렇게 하면 | 이렇게 보여야 |`)에 들어간다. 파일로 따로 만들지 않는다(프로젝트 규칙이 시나리오 파일을 요구하면 그것을 따른다).

실패 원인이 이번 작업과 무관한 기존 문제면 우회하지 말고 사용자에게 알린다. 화면 자동 테스트(Playwright)는 dev 서버가 켜져 있고 예산이 허락할 때만 [testing.md](testing.md) 대로.

## 5. PR · 리뷰 · 이슈 (git 모드, 기능 끝에 한 번)

[git-flow.md](git-flow.md) 3~10 단계:

1. 통합 브랜치 병합 → `han.mjs check --full`(관련 테스트까지) → push → PR 하나.
2. **전수 리뷰 1번** — PR 전체를 한 바퀴. 크면 리뷰어를 영역별(서버 · 관리자 · 화면)로 나눠 그 한 바퀴에 본다. 요구사항 문서가 있으면 해당 항목 대조 표를 리뷰에 넣는다.
3. PR Review 로 게시(판단 표 + 줄 단위 코멘트) → 맞는 지적을 한 번에 고친다.
4. **확인 리뷰는 맞는 「꼭 고칠 것」을 고쳤을 때만** 1번. 아니면 건너뛰고 요약에 이유를 적는다.
5. 리뷰 요약 코멘트 → 프로젝트 규칙의 이슈 절차로 이슈를 만들어 PR 과 잇는다.
6. 통합 브랜치 머지는 프로젝트 규칙과 설정 "통합 브랜치 머지" 대로(사용자가 직접 하면 멈춘다).

로컬 모드: `han-pipeline:reviewer` 로 바꾼 범위를 1번 보고, 맞는 「꼭 고칠 것」만 고친다.

## 6. 보고 · 마무리

```bash
han.mjs stop
```

보고에 넣을 것 (짧게):

0. **이번에 하지 않은 것** — 맨 위에. 화면이 예전 모양으로 남는 것, 다른 기능에 남긴 빈틈 포함.
1. 결과: PR 링크 · 리뷰 회차별 지적 수와 처리 · 이슈 번호 (로컬 모드는 커밋 나눔안과 명령).
2. 테스트 결과와 **직접 확인할 것** — 「어디를 누르면 → 무엇이 보여야」 몇 줄.
3. **사람이 할 일**: DB 마이그레이션 적용, 환경변수, 머지 등 — 명령을 그대로.
4. **학습 규칙 제안**: 이번 리뷰에서 같은 분류의 지적이 두 번 이상 나왔으면 "이 프로젝트 규칙으로 추가할까요? → `<규칙 문장>`". 승인을 받으면 설정 파일 `## 학습 규칙` 에만 더한다(리뷰 지적은 PR 에 남으므로 설정 파일에 따로 쌓지 않는다 — 브랜치마다 같은 줄을 고쳐 머지 충돌이 났다).

## 함정

| 증상 | 대처 |
| --- | --- |
| 커밋이 "[han-pipeline 검사 관문]" 으로 막힘 | `han.mjs check` 를 통과시킨다. 검사 뒤에 파일을 고쳤으면 다시 |
| PR 생성이 "check --full" 로 막힘 | PR 전에는 관련 테스트까지 넓게 — `han.mjs check --full` |
| 명령이 "사람이 직접 하는 작업" 으로 막힘 | 우회하지 않는다. 명령과 이유를 보고에 적고 멈춘다 |
| 테스트가 "Worker exited unexpectedly" | 메모리 부족. 테스트 파일을 나눠 하나씩 다시 돌린다. 계속 죽으면 사용자에게 남은 메모리와 함께 알린다 |
| "다른 무거운 일(…)이 끝나기를 기다림" | 다른 세션 · 프로젝트의 검사가 도는 중이다. 기다리는 동안 다음 코드를 고친다. 오래 걸리면 사용자에게 알린다 |
| 작업 폴더에서 린트 · 테스트 도구를 못 찾음 | 앱 폴더 node_modules 연결이 빠졌다. `worktree add` 로 새로 딴 폴더는 자동이고, 옛 폴더는 원래 폴더의 그 앱 node_modules 를 junction 으로 연결한다 |
| 서버 테스트가 설정 파일이 없다며 실패 | git 무시 파일(테스트용 application.properties 등)이 작업 폴더에 없다. 설정 "작업 폴더 복사" 에 경로를 넣는다 |
| 세션이 끊김 | 다시 부르면 `git log` · `git diff` 로 어디까지 됐는지 맞춰 잇는다. 실행 표시는 12시간 뒤 저절로 풀린다 |
| 작업 폴더에서 `git switch` 실패 | 통합 브랜치는 원래 폴더가 쓰고 있다. `git merge origin/<통합>` 으로 반영한다 |
| 파일 길이 검사 실패 | 나눈다. 나누지 않는 게 맞으면 사용자에게 알리고, 승인받은 뒤에만 설정의 `파일 길이 예외` 에 더한다 |
