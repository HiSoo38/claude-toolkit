# han-pipeline

개발 요청 하나를 **현황 파악 → 질문 한 번 → 구조 설계 → 계획 → 테스트 먼저 구현 → 검사 관문 → 화면 테스트 → 리뷰 → (git 모드) PR · 머지 → 보고** 순서로 끝까지 진행한다.
`$ARGUMENTS` 가 있으면 그것이 이번 작업이다 (파일 경로면 그 파일을 읽는다). 없으면 대화에서 사용자가 말한 작업을 쓴다.

**스크립트**: `${CLAUDE_PLUGIN_ROOT}/scripts/han.mjs`. 셸 변수는 Bash 호출 사이에 남지 않으므로 호출마다 경로를 그대로 적는다. 아래 `han.mjs <명령>` 은 `node "${CLAUDE_PLUGIN_ROOT}/scripts/han.mjs" <명령>` 의 줄임이다. 경로가 치환되지 않았으면 `~/.claude/plugins/cache/*/han-pipeline/*/scripts/han.mjs` 를 찾아 쓴다.
**셸**: 명령 예시는 Git Bash(POSIX) 기준이다. Windows PowerShell 에는 `&&` · `\` 줄 이음 · `<` 입력 연결이 없다.

## 원칙

- **사용자가 가져온 문서가 기준이다.** 요구사항 · DB 설계 · API 명세 · 시안을 받았으면 그대로 따른다. 다시 쓰거나 형식을 바꾸지 않는다.
- **구조를 먼저 정하고 짓는다.** 코드 분리는 나중에 몰아서 하지 않는다. 계획서의 "구조 설계" 가 비어 있으면 구현을 시작하지 않는다.
- **검사는 스크립트가, 관문은 훅이 한다.** 검사는 `han.mjs check` 로 한다. 이 플러그인의 훅이 검사를 통과하지 않은 커밋 · PR 생성을 막는다.
- **사용자가 다른 작업을 계속할 수 있게 돈다.** `start` 가 보여 주는 자원 예산을 이번 실행 내내 지킨다.
- **사람만 하는 일은 하지 않는다.** 배포 브랜치 머지 · push, force push, DB 적용 · 직접 쿼리, 운영 배포 · 환경변수 · 비밀값 변경, 원격 저장소 생성. 실행할 명령을 적어 보여 주고 멈춘다. 훅도 이 명령들을 막는다.
- **통합 · 배포 브랜치에서는 커밋하지 않는다.** 변경을 올리지 말라는 게 아니라, 이 두 브랜치 위에서 고쳐 바로 커밋 · push 하지 않는다는 뜻이다. 한 줄짜리 문서 · 설정 수정, 머지 뒤 남은 체크리스트 정리도 `feature/` · `fix/` · `docs/` 브랜치(또는 작업 폴더)를 따서 커밋하고 PR 로 올린다. 통합 브랜치에는 PR 머지로만 변경이 들어간다. 통합 브랜치에서 하는 git 작업은 `pull` 과 브랜치 따기뿐이다. 훅도 두 브랜치의 커밋과 통합 브랜치 push 를 막는다.
- **프로젝트 규칙이 이긴다.** 프로젝트 `CLAUDE.md` · `AGENTS.md` 를 먼저 읽는다. 같은 주제(브랜치 · 계획서 형식 · 커밋 · 리뷰 횟수 · 머지)의 규칙이 있으면 그것을 따르고, 이 스킬의 단계 중 프로젝트 흐름에 없는 것(현황 파악 · 구조 설계 · 테스트 먼저 · 검사 관문 · 화면 테스트 · 자원 예산)을 그 사이에 끼워 넣는다.

## 1. 모드 고르기

| 모드 | 언제 | git · gh |
| --- | --- | --- |
| **git 모드** | 이번 요청에 git 흐름을 맡기는 말이 있다: "올려줘", "PR", "머지까지", "브랜치로", 또는 프로젝트 규칙이 git 흐름의 시작 문구로 적어 둔 말과 같은 뜻의 요청 | 브랜치 · 커밋 · push · PR · 리뷰 게시 · 통합 브랜치 머지까지 한다. 이 스킬을 그렇게 부른 것이 git 지시다 |
| **로컬 모드** | 그 밖 ("만들어줘", "구현해줘", "고쳐줘"). 프로젝트 규칙에 git 흐름이 있어도, 이번 요청에 git 을 맡기는 말이 없으면 로컬 모드다 | git 상태를 바꾸는 명령(add · commit · switch · stash · push 등)과 gh 쓰기를 하지 않는다. 지금 작업 트리에서 끝까지 하고, 마지막에 커밋 나눔안과 명령을 보여 주고 멈춘다. 지금 브랜치가 통합 · 배포 브랜치면 그 명령의 맨 앞에 새 브랜치 따기(`git switch -c feature/<작업-이름>`)를 넣는다 |
| **이어하기** | "이어서 해줘", "계속해줘" | 이어 가는 체크리스트 머리의 `모드:` 값을 따른다 (아래 2 단계) |

**기능이 둘 이상이면**: git 모드에서는 [parallel.md](parallel.md) 대로 기능마다 작업 폴더(git worktree) · 브랜치 · Claude 를 따로 두고 동시에 진행한다. Orca 가 켜져 있으면 작업공간마다 Claude 를 띄워 사용자가 화면에서 보고, 없으면 이 세션의 하위 에이전트가 맡는다. 겹치는 기능은 차례로 묶고, 통합 브랜치 머지는 이 세션이 하나씩 한다. 로컬 모드에서는 하나씩 차례로 한다.
**병렬 하위 작업으로 불렸으면** (지시문이 "han-pipeline 의 병렬 하위 작업이다" 로 시작): [parallel.md](parallel.md) "하위 작업 규칙" 이 이 문서보다 우선한다.

## 2. 시작

```bash
git status -sb
han.mjs start            # 새 작업. 이어하기면 han.mjs start --resume
```

`start` 는 실행 표시를 켜고 설정 · 자원 예산 · **시작 전부터 바뀌어 있던 파일** 목록을 보여 준다. 그 파일들은 남의 작업일 수 있으므로 건드리지 않는다 (검사에서도 빠진다). git 모드인데 그 목록이 있으면 브랜치를 바꾸기 전에 멈추고 묻는다.

**이어하기**

1. 대상: 사용자가 작업 이름을 말했으면 그것. 아니면 계획서 위치에서 "구현" · "테스트" 칸과 그 체크리스트 모드의 "리뷰" 칸에 `- [ ]` 가 남은 폴더 중 최근 것. 후보가 둘 이상이면 묻는다.
2. 모드 · 브랜치: 체크리스트 머리의 `모드:` · `브랜치:` 를 따른다. git 모드면 "git 모드로 이어갑니다 (브랜치 <이름>)" 라고 한 줄 알리고 그 브랜치로 옮긴다.
3. 상태 맞추기: plan.md(특히 구조 설계)와 설정의 학습 규칙을 다시 읽는다. `[x]` 항목이 실제로 있는지(git 모드는 `git log`, 로컬 모드는 파일)와 다음 항목이 반쯤 되어 있는지(`git diff`)를 확인하고 거기서부터 잇는다. explorer 는 구조 설계를 바꿔야 할 때만 다시 부른다.

**자원 예산** — `start` 출력의 값을 따른다. 측정은 실행하는 사람의 PC 에서 매번 새로 한다.

- 무거운 일(타입 검사 · 린트 · 테스트 · 브라우저 · Codex · 패키지 설치)은 **한 번에 하나**만. 검사는 `check`, 그 밖의 무거운 명령은 `han.mjs run "<명령 전체>"` 로 실행한다 (남은 메모리 확인 · 낮은 우선순위 · 힙 한도). 둘 다 PC 전체 잠금으로 줄을 서서, 다른 세션 · 작업 폴더의 검사가 돌고 있으면 끝날 때까지 기다린다. Codex 는 원격에서 계산해 줄을 서지 않고 바로 돈다.
- 리뷰어 동시 실행, 화면 자동 테스트 실행 여부는 예산의 값대로.
- 전체 빌드(`next build`, `vite build`, `gradlew build` 등)와 전체 테스트는 돌리지 않는다. 필요하면 묻는다.
- dev 서버를 새로 켜지 않는다. 켜져 있는지는 설정의 `dev 서버 주소` 에 한 번 요청해서 본다 (`curl -s -o /dev/null -w "%{http_code}" --max-time 5 <주소>`). 꺼져 있으면 화면 테스트를 사람 확인으로 넘긴다.
- 통과한 뒤 파일이 안 바뀐 검사는 다시 돌리지 않는다.

## 3. 현황 파악

| 상황 | 할 일 |
| --- | --- |
| 소스 코드가 거의 없는 새 프로젝트 | [setup.md](setup.md) "기반 작업" 을 먼저 한다. 설정 파일은 기반 작업 끝에 만든다 |
| 진행 중인 프로젝트, 설정 파일(`<저장소>/.claude/han-pipeline.md`) 없음 | [setup.md](setup.md) "설정 파일 만들기" |
| 그 밖 | 아래로 |

**입력 문서**

- 사용자가 문서를 주었으면 계획서 "입력 문서" 칸에 경로를 적고, 계획은 그 문서의 항목을 가리키기만 한다 (예: "요구사항 3.2 → 체크리스트 2~4번"). 원본은 고치지 않는다.
- 문서에 없는 것은 계획서 "결정 사항 — 에이전트가 정함" 에 기본안으로 적고 진행한다.
- 문서가 없으면 대화 내용만으로 계획서를 쓴다. 요구사항 · 스키마 · API 문서를 따로 만들지 않는다.

**크기**

| 크기 | 기준 | 다른 점 |
| --- | --- | --- |
| 작음 | 파일 1~3개, DB · API 변경 없음 | 계획서를 짧게 (목적 · 구조 설계 · 테스트 계획). 프로젝트 규칙이 리뷰 횟수를 정하지 않았으면 확인 리뷰는 맞는 "꼭 고칠 것" 이 있을 때만 |
| 중간 | 그 밖 | 아래 단계 그대로 |
| 큼 | DB 테이블 2개 이상 변경, 화면 3개 이상, 또는 체크리스트가 15항목을 넘음 | 계획서까지 쓰고 사용자 승인을 받는다. 체크리스트를 독립적으로 머지할 수 있는 묶음으로 나눈다 (계획서 하나, 묶음마다 브랜치 · PR 하나) |

**질문은 여기서 한 번에** — 아래 중 해당하는 것만 모아 AskUserQuestion 한 번(최대 4개)으로 묻는다. 그 밖에서는 묻지 않고 기본안으로 간다.

- 문서끼리 또는 문서와 기존 코드가 부딪히는 점, 문서만으로 정할 수 없어 구현이 막히는 점
- 화면 자동 테스트 범위 (설정 파일을 새로 만들 때)
- 테스트 도구 설치 (단위 · 화면 테스트 도구가 없을 때, [testing.md](testing.md))
- 새 프로젝트의 스택 (정해진 게 없을 때)

## 4. 구조 설계 (코드 분리 기본)

1. `han-pipeline:explorer` 를 부른다 (작업 설명, 루트, 설정의 공용 디렉터리 · 파일 길이 한도). 이번 실행에서 설정 파일을 만들며 이미 불렀으면 그 결과를 쓴다.
2. 계획서 "구조 설계" 의 네 칸을 채운다: **재사용할 기존 코드 / 새로 만들 공용 코드 / 파일 배치 / 커질 위험과 나눌 방법**.
3. 판단 기준:
   - 이미 있으면 가져다 쓴다. 조금 넓히면 쓸 수 있으면 넓힌다 (기존 사용처가 깨지지 않는지 확인).
   - 두 곳 이상에서 쓸 것은 공용 디렉터리로, 한 기능에서만 쓰는 것은 그 기능 폴더에 둔다.
   - 너무 잘게 쪼개지 않는다. 관련된 것이 흩어져 파일을 타고 들어가야 하면 과분리다.
   - 애매하면 "다른 사람이 코드만 보고 이해할 수 있는가" 로 정한다. 프로젝트의 기존 스타일을 따른다.
4. 네 칸 중 하나라도 비어 있으면 구현을 시작하지 않는다. 해당 없음이면 "없음 — <이유>".

## 5. 계획서 · 체크리스트

`<계획서 위치>/YYYY-MM-DD-<작업-이름>/plan.md` · `checklist.md` · `test-scenarios.md`.

- 형식: 프로젝트 규칙에 계획서 형식이 있으면 그 형식을 쓰고, 이 스킬의 필수 칸(입력 문서 · 구조 설계 · 테스트 계획의 "방법" 열, 체크리스트 머리의 `모드:`)을 더한다. 없으면 [templates/plan.md](templates/plan.md) · [templates/checklist.md](templates/checklist.md). 체크리스트에는 이번 모드의 "리뷰" 칸만 남긴다.
- 체크리스트 항목 하나 = 커밋 하나로 끝낼 수 있는 크기. 항목마다 테스트 방법(단위 / 화면 / 사람)을 적는다.
- `test-scenarios.md` 는 [templates/test-scenarios.md](templates/test-scenarios.md) 로 만든다. 사람이 그대로 밟으며 확인하는 파일이다 — 기능마다 `| # | 이렇게 하면 | 이렇게 보여야 | 결과 |` 표 하나, 한 줄에 동작 하나. 이 단계에서는 기능 제목과 확인할 동작만 적고, 구현하면서 실제 버튼 이름 · 주소 · 문구로 채운다. 요구사항 ID · 자동 테스트 이름 · 설명은 표에 넣지 않고 맨 아래 「참고」에만 모은다.
- 계획서는 저장소에 올라갈 수 있다. 비밀값 · 이메일 · 개인 신상 · 고객 데이터는 `<비밀값>` 처럼 가린다.
- 승인이 필요하면(크기 "큼" 이거나 사용자가 "계획 먼저 보여줘") 파일만 쓴 채로 `han.mjs stop` 하고 멈춘다. 승인 뒤 이어하기로 돌아온다.
- git 모드: [git-flow.md](git-flow.md) 1 단계로 브랜치를 따고 이 세 파일을 첫 커밋으로 올린다 (승인이 필요했으면 승인 뒤에).

## 6. 구현 (항목마다 반복)

1. **테스트 먼저** ([testing.md](testing.md)):
   - "단위" 항목: 테스트를 쓰고 실패하는 것을 확인한다.
   - "화면" 항목: Playwright 테스트를 쓴다 (실행은 7 단계에서 몰아서).
   - "사람" 항목: 테스트를 쓰지 않는다.
2. 구현한다. 구조 설계에 적은 위치 · 재사용을 따른다. 설계를 바꿔야 하면 plan.md 를 먼저 고친다.
3. `han.mjs check` — 실패하면 고치고 다시. 실패 원인이 이번 작업과 무관한 기존 문제(이번에 안 바꾼 곳의 타입 오류 등)면 우회하지 말고 멈춰서 사용자에게 알린다.
4. `test-scenarios.md` 의 그 기능 표를 실제 화면대로 채운다 — 정상 흐름 줄과 예외 · 경계 줄(비로그인 · 빈 값 · 실패 · 모바일 폭 · 키보드). 결과 칸은 ⬜ 로 둔다(사람이 ✅ / ❌ 로 바꾼다). 자동 테스트로 확인한 줄도 지우지 않는다 — 사람이 화면에서 한 번 더 볼 수 있게.
5. 체크리스트를 `[x]` 로 바꾼다. git 모드면 [git-flow.md](git-flow.md) 2 단계대로 커밋한다 (테스트 파일 · 시나리오는 그 코드와 같은 커밋에).

계획이 바뀌면 plan.md 를 고치고 checklist.md 에 항목을 더하거나 `~~취소~~` 로 남긴다 (지우지 않는다). 리뷰 · 사용자 요청으로 동작이 바뀌면 `test-scenarios.md` 의 그 줄도 같이 고친다.

## 7. 화면 테스트

[testing.md](testing.md) "화면 자동 테스트" 대로 `han-pipeline:tester` 로 돌린다. 예산이 건너뛰라고 하거나 dev 서버가 꺼져 있으면 그 항목들을 사람 확인으로 넘긴다.

## 8. 리뷰

- **git 모드**: [git-flow.md](git-flow.md) 3~10 단계 — 통합 브랜치 반영 · PR → 전수 리뷰(Codex + `han-pipeline:reviewer`) → PR 리뷰 게시 → 한 번에 수정 → 확인 리뷰 → 리뷰 요약 → 통합 브랜치 머지 → 통합→배포 PR.
- **로컬 모드**: `han-pipeline:reviewer` 로 1번 ([review-prompt.md](review-prompt.md) 전수, 범위는 `git diff HEAD` 와 새 파일, 시작 전부터 바뀌어 있던 파일 제외). 맞는 "꼭 고칠 것" 을 고친 뒤 `check`.

## 9. 보고 · 마무리

```bash
han.mjs stop
```

보고에 넣을 것:

1. 결과: 한 일. git 모드는 PR 링크와 리뷰 회차별 지적 수 · 처리. 로컬 모드는 커밋 나눔안 — 커밋별 파일 · 메시지와 실행할 명령 (프로젝트 커밋 규칙대로).
2. **코드 분리 점검**: 재사용한 것, 새로 만든 공용 코드, 한도를 넘어 나눈 파일.
3. **테스트 결과**: 단위 테스트 수 · 통과, 화면 자동 테스트 항목별 ✅/❌, **직접 확인할 것** — `test-scenarios.md` 경로와 기능별 줄 수. 자동으로 못 본 줄만 몇 개 골라 "어디를 누르면 → 무엇이 보여야 하는지"로 다시 적는다.
4. **사람이 할 일**: DB 마이그레이션 적용, 환경변수, 배포 브랜치 머지, 미룬 설치 등 — 명령을 그대로.
5. **학습 규칙 제안**: 아래에서 나온 것.

## 학습 규칙

프로젝트마다 다르므로 그 프로젝트의 설정 파일에만 쌓는다.

- 리뷰에서 "맞음" 으로 판단한 지적은 설정 파일 `## 리뷰 지적 기록` 에 한 줄씩 남긴다: `- YYYY-MM-DD <분류> — <요지> (<파일>)`. 분류는 짧은 이름(예: 공용 컴포넌트 중복, 에러 처리 누락)으로 한다.
- 같은 분류가 기록에 **두 번 이상** 있으면 보고에서 묻는다: "이 프로젝트 규칙으로 추가할까요? → `<규칙 문장>`".
- 사용자가 승인했을 때만 `## 학습 규칙` 에 더한다. 여러 프로젝트에 통할 습관으로 보이면 사용자 전역 설정(`~/.claude/CLAUDE.md`)에 넣을지도 따로 제안한다.

## 함정

| 증상 | 대처 |
| --- | --- |
| 커밋이 "[han-pipeline 검사 관문]" 으로 막힘 | `han.mjs check` 를 통과시킨다. 검사 뒤에 파일을 고쳤으면 다시 |
| 명령이 "사람이 직접 하는 작업" 으로 막힘 | 우회하지 않는다. 명령과 이유를 보고에 적고 멈춘다 |
| 세션이 끊김 | 다시 부르면 이어하기. 실행 표시는 12시간 뒤 저절로 풀린다 |
| `check` 가 "메모리 기다림" | 사용자 몫을 지키는 중이다. 1분 뒤에는 낮은 우선순위로 진행한다 |
| "다른 무거운 일(…)이 끝나기를 기다림" | 다른 세션 · 작업 폴더의 검사가 도는 중이다. 기다린다. 잠근 프로세스가 죽었으면 저절로 풀린다 |
| 작업 폴더에서 `git switch` 실패 | 통합 브랜치는 원래 폴더가 쓰고 있다. 브랜치를 바꾸지 말고 `git merge origin/<통합>` 으로 반영한다 |
| 파일 길이 검사 실패 | 구조 설계대로 나눈다. 나누지 않는 게 맞으면 사용자에게 알리고, 승인받은 뒤에만 설정의 `파일 길이 예외` 에 더한다 |
