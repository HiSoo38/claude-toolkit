# /build — 요구사항 하나로 끝까지

입력: `$ARGUMENTS`

이 커맨드가 파이프라인 전체를 진행한다. 다른 dev-pipeline 커맨드(`init-pipeline`, `plan-tasks`, `review-plan`, `run-wave`)는 **Skill 도구로 부르지 않고**, 그 SKILL.md 를 Read 해서 아래에 적은 차이만 바꿔 직접 실행한다 (그 커맨드들은 사용자 실행 전용이라 Skill 도구로 불러지지 않는다).

- `${CLAUDE_PLUGIN_ROOT}/skills/<이름>/SKILL.md`

## 원칙

- **사람에게 묻는 건 한 번만** (3단계 확인). 그 전 단계에서는 묻지 않고 합리적인 기본값으로 진행하고, 고른 기본값은 3단계에서 한꺼번에 보여준다. 예외: 요구사항이 아예 없을 때, 0단계에서 이미 진행 중인 다른 계획과 충돌할 때.
- **기존 코드가 기준이다.** 이미 구현된 프로젝트면 지금 코드가 하는 일(DB 구조, API, 기능)을 먼저 계약 문서에 "기존" 으로 옮기고, 이번 요구는 그 위에 더하는 변경으로 적는다. 기존 동작을 바꾸는 요구만 변경으로 표시한다.
- **멈춰야 하는 이유가 아니면 멈추지 않는다.** 판단할 수 없는 점은 기본안을 정해 "미정 사항" 에 `- [ ] 질문 — 기본안: <값>` 으로 남기고 진행한다.
- 3단계에서 사람이 승인하면 그 승인이 이번 실행의 **git 지시**다: 기준 브랜치에 계획 문서 커밋, Orca 에 레포 등록, (자동 머지를 고르면) 웨이브 사이 로컬 머지. push 는 여기 포함되지 않는다 — 마지막에 한 번 묻는다.
- 커밋 · 머지 메시지는 이 세션에 로드된 **사용자의 커밋 규칙**(전역 · 프로젝트 CLAUDE.md, CLAUDE.local.md)을 따르고, 없을 때만 `type(scope): 요약` + 이유 · 근거.
- 매 단계 시작과 끝을 진행 로그(`<공용 git 폴더>/dev-pipeline/progress.log`, `git rev-parse --path-format=absolute --git-common-dir`)에 "<YYYY-MM-DD HH:MM>  [build]  <단계> — <한 줄>" 로 남기고, 사용자에게도 한 줄로 알린다.

## 0단계 — 어디까지 했는지 확인 (이어하기)

아래를 위에서부터 확인해 **처음으로 끝나지 않은 단계**부터 시작한다. 확인 결과를 표 하나로 보여준다 (단계 · 상태 · 근거).

| 확인 | 끝났다고 보는 조건 | 아니면 |
| --- | --- | --- |
| git 레포 | `git rev-parse --show-toplevel` 성공 | 멈추고 "git 레포에서 실행하세요" |
| 준비 | 프로젝트 CLAUDE.md "기술 스택" 이 채워져 있음 | 1단계 |
| 계약 문서 | 세 문서가 있고, 이번 요구사항의 기능이 requirements 기능 목록에 있음 | 2단계 |
| 계획 | `docs/tasks/plan.md` · `checklist.md` · 카드가 있고 이번 기능이 모두 작업에 배정됨, `plan-review.md` 가 통과이고 지문이 지금 파일과 같음 | 2.5단계 |
| 승인 · 커밋 | `git status --short -- docs CLAUDE.md AGENTS.md` 가 비어 있고 진행 로그에 "[build] 승인" 줄이 있음 | 3단계 |
| 웨이브 | 모든 작업이 머지됨 (`run-wave` 1단계 "머지 판정") | 4단계 (진행 중 · 멈춘 작업이 있으면 5단계부터) |

- `$ARGUMENTS` 가 비어 있으면 이어하기다. 진행 중인 계획도 없으면 "무엇을 만들지 요구사항을 알려 주세요" 라고 묻고 멈춘다.
- `$ARGUMENTS` 가 파일 경로면 그 파일을 요구사항으로 읽는다.
- `$ARGUMENTS` 가 있고 이미 끝나지 않은 계획(머지 안 된 작업)이 있으면: 이번 요구가 그 계획의 기능이면 이어하기, 다른 요구면 AskUserQuestion 으로 "진행 중인 계획 뒤에 이어서 추가 / 진행 중인 계획을 버리고 새로 / 취소" 를 묻는다.
- 진행 로그의 `[build]` 줄과 `docs/tasks/results/` 도 참고해 마지막으로 끝난 단계를 판단한다.

## 1단계 — 준비 (init-pipeline 자동 모드)

`init-pipeline/SKILL.md` 를 Read 하고 그 절차대로 하되, **묻지 않는다**:

- 스택 감지 결과는 그대로 쓴다 (확인 질문 생략). 근거가 충돌하거나 감지가 안 된 항목만 `<!-- TODO -->` 로 두고 3단계에서 보여준다. 언어조차 판단할 수 없는 빈 프로젝트면 요구사항에 적힌 기술을 쓰고, 그것도 없으면 이때만 init-pipeline 2단계 질문을 한다.
- 이미 있는 파일: CLAUDE.md · AGENTS.md 는 "빠진 섹션만 추가", docs/ 계약 문서는 있으면 그대로 두고 없을 때만 템플릿을 쓴다. 덮어쓰지 않는다.
- **기준 브랜치**를 실제 레포에서 정한다: `git symbolic-ref --short refs/remotes/origin/HEAD` 의 `origin/` 뒤 이름 → 없으면 `main`·`master`·`develop` 중 있는 것 → 없으면 현재 브랜치. CLAUDE.md "파이프라인 설정" 의 `기준 브랜치` 에 적는다.
- "공용 코드 위치" · "코딩 컨벤션" · "빌드·테스트 명령" 을 기존 코드에서 찾아 채운다 (공통 컴포넌트 · 유틸 디렉터리, 린터 설정, package 스크립트 등).

## 2단계 — 계약 문서 (기존 상태 + 이번 요구)

소스 코드가 있는 프로젝트면 먼저 **기존 상태 반영**을 한다 (한 번만 — requirements 에 "기존" 기능이 이미 있으면 건너뛴다). 아래 세 에이전트를 순서대로 Agent 도구로 부른다. 프롬프트 맨 앞에 "**기존 코드 반영 모드**" 를 적는다 (각 에이전트 정의에 이 모드의 규칙이 있다).

1. `dev-pipeline:planner` — 기존 코드의 화면 · 라우트 · 서비스를 보고 지금 있는 기능을 기능 목록에 "기존" 으로 적고, 이어서 이번 요구사항(`$ARGUMENTS` 전문)을 새 기능 ID 로 더한다. 기존 기능을 바꾸는 요구는 그 기능 행에 "변경" 으로 표시한다.
2. `dev-pipeline:db-designer` — 마이그레이션 · ORM 모델 · 엔티티 · SQL 파일에서 지금 스키마를 옮겨 적고("기존"), 이번 기능에 필요한 테이블 · 컬럼만 더한다("신규" / "변경"). DB 가 없으면 건너뛴다.
3. `dev-pipeline:api-designer` — 라우터 · 컨트롤러에서 지금 API 를 옮겨 적고("기존"), 이번 기능의 엔드포인트만 더한다.

새 프로젝트(소스 코드 없음)면 "기존 코드 반영 모드" 없이 같은 순서로 이번 요구만 쓴다.

세 에이전트 모두 판단할 수 없는 점은 기본안을 정해 미정 사항에 `- [ ] 질문 — 기본안: <값>` 으로 남기게 한다. 에이전트 보고에서 미정 사항을 모아 둔다 (3단계에서 묻는다).

## 2.5단계 — 계획과 계획 리뷰 (plan-tasks 자동 모드)

`plan-tasks/SKILL.md` 를 Read 하고 그 절차대로 하되:

- 0단계 3번 경고(초안 · 미정 사항 남음)는 묻지 않고 계속한다. 계획 리뷰는 `--allow-draft` 로 돌린다 (3단계의 사람 승인이 초안 진행 승인이다).
- 0단계 4번: `plan.md` 가 이미 있으면 묻지 않고 "기존 작업은 두고 새 작업만 추가" 로 한다. 새 작업 번호는 기존 번호 뒤에 잇는다. 이미 머지된 작업은 다시 계획하지 않는다.
- 기존 프로젝트면 1단계에서 기능마다 **실제로 고쳐야 할 기존 파일**을 Grep 으로 찾아 담당 범위에 넣는다 (새 파일만 만드는 계획이 되지 않게). 같은 기존 파일을 여러 기능이 고쳐야 하면 한 작업으로 묶거나 의존 순서를 건다.
- 5단계 계획 리뷰: `review-plan/SKILL.md` 를 Read 해서 `--allow-draft` 로 실행한다. 블로커가 나오면 계획 문서로 고칠 수 있는 것은 고치고 다시 리뷰한다 (최대 2회). 계약 문서를 고쳐야 하는 블로커는 담당 에이전트(planner / db-designer / api-designer)를 다시 불러 고치게 한 뒤 다시 리뷰한다 (최대 1회). 그래도 남으면 3단계에서 보여준다.
- 7단계 GitHub 이슈는 하지 않는다.

## 3단계 — 사람 확인 (한 번)

아래를 한 화면으로 보여준다.

```markdown
## 진행 전 확인

- 프로젝트: <루트> · 기준 브랜치: <기준> · 스택: <언어 / 프레임워크 / DB / 테스트>
- 기존 상태 반영: 기능 <n>개 · 테이블 <n>개 · API <n>개 (계약 문서에 "기존" 으로 기록)
- 이번 요구: <새 기능 ID · 이름 목록> / 기존 기능 변경: <목록 또는 없음>
- DB 변경: <신규 · 변경 테이블과 컬럼> · API 변경: <신규 · 변경 엔드포인트>

| 작업 | 제목 | 웨이브 | 의존 | 고치는 주요 파일 |
| --- | --- | --- | --- | --- |

- 계획 리뷰: <판정> (리뷰어 <…>, 남은 블로커 <목록 또는 0>)
- 기본값으로 정한 것: <미정 사항의 기본안 목록 · TODO 로 남은 스택 항목>
```

그리고 AskUserQuestion 한 번으로 묻는다 (질문 최대 4개):

1. "이 계획대로 진행할까요?" — `진행 (웨이브 사이 자동 머지) (Recommended)` / `진행 (머지는 내가 함)` / `계획 수정` / `취소`
   - 자동 머지: 각 웨이브의 작업이 리뷰를 통과하고 커밋되면 이 세션이 기준 브랜치에 로컬 머지하고 다음 웨이브를 띄운다. push 는 하지 않는다.
2~4. 기본안을 바꿀 가능성이 큰 미정 사항 순서로 최대 3개 (선택지: 기본안 (Recommended) / 다른 안 1~2개). 나머지 미정 사항은 기본안으로 간다.

답에 따라:

- `계획 수정` · 기타 입력: 사용자가 적은 내용대로 계약 문서(담당 에이전트) · 계획을 고치고 2.5단계 계획 리뷰를 다시 한 뒤 3단계로 돌아온다.
- 미정 사항을 기본안과 다르게 고르면: 담당 에이전트로 그 문서를 고치고, 영향받는 계획 문서를 고치고, 계획 리뷰를 다시 돌린다 (지문이 바뀌기 때문). 다시 묻지는 않는다 — 결과만 보여주고 진행한다. 블로커가 생기면 그때 멈춘다.
- `취소`: 문서는 그대로 두고 멈춘다.
- 승인되면 진행 로그에 "[build] 승인 — <자동 머지 | 사람 머지>" 를 남긴다. 이 줄이 0단계 이어하기의 근거다.

AskUserQuestion 을 쓸 수 없으면(비대화형) 위 확인 화면과 질문을 출력하고 멈춘다. 사용자가 답하면 이어간다.

## 3.5단계 — 문서 커밋과 Orca 준비

1. 현재 브랜치가 기준 브랜치가 아니면 멈추고 "기준 브랜치(<기준>)에서 실행하세요" 라고 알린다 (브랜치를 바꾸지 않는다).
2. `docs/`, `CLAUDE.md`, `AGENTS.md` 의 변경만 스테이징해 사용자 커밋 규칙대로 커밋한다 (규칙에 따라 나눈다 — 예: 파이프라인 설정 / 계약 문서 / 계획 문서). 그 밖의 파일은 스테이징하지 않는다. 훅을 건너뛰지 않는다.
3. `orca status --json` 의 `result.runtime.reachable` 이 `true` 가 아니면 "Orca 앱을 켜 주세요" 라고 알리고 멈춘다 (켠 뒤 다시 실행하면 여기서부터 이어간다).
4. `orca repo list --json` 에 `<루트>` 가 없으면 `orca repo add --path <루트> --json` 으로 등록한다.

## 4단계 — 웨이브 띄우기 (run-wave 자동 모드)

`run-wave/SKILL.md` 를 Read 하고 인자 `--yes --allow-draft --no-push` 로 실행한다.

- `--no-push`: 각 작업은 커밋까지 하고 push 를 묻지 않는다 (사람이 각 탭에서 답하느라 작업이 멈추지 않게). push 는 7단계에서 한 번 묻는다.
- 진행 로그에 "[build] 웨이브 <n> 시작 — <작업들>" 을 남긴다.

## 5단계 — 기다리기

띄운 작업(또는 0단계에서 찾은 진행 중 작업)의 브랜치로 감시 스크립트를 **백그라운드로** 실행한다 (Bash `run_in_background`):

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/wait_wave.py" --repo "<루트>" --branches <브랜치1>,<브랜치2> --interval 60 --stall-min 15
```

`python` 이 없으면 `python3`. 실행했으면 "웨이브 <n> 작업 중 — Orca 왼쪽 목록에서 각 작업 탭을 볼 수 있고, 끝나면 이 창이 이어서 진행합니다" 라고 알리고 턴을 마친다. 스크립트가 끝나면 이 세션이 다시 깨어난다. 그때 출력 JSON 의 `tasks` 로 6단계를 한다.

## 6단계 — 웨이브 정리

작업마다 `state` 에 따라:

| state | 처리 |
| --- | --- |
| `done` | 작업 브랜치에 커밋이 있는지 확인 (`run-wave` "머지 판정" 의 생성 커밋 이후 커밋 수). 없으면(테스트 미검증 · 커밋 대기) "사람 확인 필요" 로 둔다 |
| `stalled` | 그 worktree 터미널(`orca terminal list --worktree path:<path> --json`)의 마지막 출력을 `orca terminal read --terminal <handle> --limit 40 --json` 으로 읽는다. 사용량 한도면 "한도가 풀리면 다시 `/dev-pipeline:build` 를 실행하세요" 로 둔다. 질문 대기면 그 질문을 사용자에게 보여준다. 그 밖(멈춤 · 종료)이면 `orca terminal send --terminal <handle> --text "/dev-pipeline:work-task T<번호> <원래 인자>" --enter --json` 으로 **한 번** 다시 시작시키고 그 작업만 5단계로 다시 기다린다 (`work-task` 는 끝난 단계를 건너뛴다). 살아 있는 터미널이 없으면 사용자에게 Orca 의 그 작업 탭에서 `claude` 를 열고 `/dev-pipeline:work-task T<번호>` 를 실행해 달라고 알린다 |
| `attention` | 코멘트와 그 worktree 의 `docs/tasks/results/T<번호>.md` 요약을 보여준다 — 사람이 판단할 부분 |
| `missing` · `timeout` · `orca-unreachable` | 이유를 알린다 |

자동 머지를 승인받았으면, `done` 이고 커밋이 있는 작업을 작업 번호 순으로 기준 브랜치에 머지한다:

1. 메인 체크아웃(기준 브랜치)에서 `git status --short` 가 비어 있는지 확인한다. 아니면 머지하지 않고 알린다.
2. `git merge --no-ff <브랜치>` (메시지는 사용자 커밋 규칙대로 — 기본은 `merge(T<번호>): <제목>` + 리뷰 판정 · 테스트 결과). 충돌이 나면 `git merge --abort` 로 되돌리고 그 작업을 "사람 확인 필요 — 머지 충돌 (<파일>)" 로 둔다. 충돌을 직접 풀지 않는다.
3. 이 웨이브를 다 머지한 뒤 CLAUDE.md 의 빌드 명령이 가벼운 단일 프로세스 검사(타입 검사 등)로 대신할 수 있으면 그것만 한 번 돌린다. 무거운 전체 빌드는 돌리지 않는다. 실패하면 다음 웨이브를 띄우지 않고 알린다.
4. 진행 로그에 "[build] 웨이브 <n> 머지 — <작업들>" 을 남긴다.

그다음:

- 사람 확인이 필요한 작업이 있으면 그 목록과 할 일을 보여주고 멈춘다. 사람이 처리한 뒤 `/dev-pipeline:build` 를 다시 실행하면 이어간다.
- 머지는 사람이 하기로 했으면 검수 · 머지할 브랜치 목록을 보여주고 멈춘다 (머지한 뒤 다시 실행하면 다음 웨이브).
- 그 밖이면 남은 웨이브가 있을 때 4단계로 돌아간다. 없으면 7단계.

## 7단계 — 마무리

- 전체 결과: 작업별 결과 · 커밋 · 머지, 리뷰 판정, 남은 권장 사항 (`docs/tasks/results/` 요약).
- 사람이 확인할 것: 바뀐 기능을 직접 눌러 볼 테스트 체크리스트 (화면 · API 마다 "어디서 무엇을 하면 → 무엇이 보여야 함").
- AskUserQuestion 으로 "기준 브랜치(<기준>)를 원격에 push 할까요?" (push / 나중에). 원격이 없으면 묻지 않는다. 승인하면 `git push <remote> <기준>` (`--force` 금지).
- 진행 로그에 "[build] 완료" 를 남긴다.

## 하지 않는 것

- 3단계 승인 없이 커밋 · 머지 · Orca 레포 등록.
- 묻지 않은 push, `--force`, rebase · reset, 머지 충돌 직접 해결, PR 생성.
- 코드 직접 수정 (구현은 각 worktree 의 implementer, 계약 문서는 담당 에이전트).
- 무거운 전체 빌드 · 전체 테스트.
