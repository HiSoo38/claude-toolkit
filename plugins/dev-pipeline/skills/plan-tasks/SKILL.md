# /plan-tasks — 계획서 · 구현 체크리스트 · 작업 카드

추가 지시: $ARGUMENTS

만드는 문서는 셋이다. 셋 다 `docs/tasks/` 에 둔다.

| 문서 | 내용 | 누가 쓰나 |
| --- | --- | --- |
| `plan.md` (계획서) | 목표와 범위, 구현 방식과 작업 간 공통 약속, 작업·웨이브 표, 공유 파일 소유, 테스트 전략, 위험 | 사람(검토·승인), plan-reviewer |
| `checklist.md` (구현 체크리스트) | 작업마다 순서대로 따라 하면 구현이 끝나는 항목 (`T<번호>-<순번>`) | implementer(따라 구현), reviewer(항목별 대조) |
| `T<번호>.md` (작업 카드) | 작업 하나의 담당 파일 범위, 범위 밖, 완료 조건 | `/run-wave` · `/work-task` |

## 0단계 — 사전 확인

1. 프로젝트 `CLAUDE.md` 를 읽는다. "기술 스택" 섹션이 없거나 값이 전부 `<!-- TODO -->` 면 **멈추고** "먼저 `/dev-pipeline:init-pipeline` 을 실행하세요" 라고 안내한다.
2. CLAUDE.md "계약 문서" 표에서 세 문서 경로를 읽는다 (없으면 `docs/requirements.md`, `docs/schema.*`, `docs/api-spec.md`). "파이프라인 설정" 에서 동시 작업 수(없으면 3)와 기준 브랜치(없으면 `main`)를 읽는다.
3. 세 문서를 읽는다. 다음이면 경고하고 계속할지 묻는다:
   - 문서가 없거나 비어 있음
   - 상태가 "확정" 이 아님
   - "미정 사항" 에 체크 안 된 항목이 남아 있음

   (dev-pipeline 규칙: 계약 확정 전에는 기능 구현을 시작하지 않는다. 단 프로젝트 세팅·공통 모듈 작업은 계획해도 된다.)
4. `docs/tasks/plan.md` 가 이미 있으면 읽고, 다시 계획할지(기존 문서 덮어쓰기) / 기존 작업은 두고 새 작업만 추가할지 묻는다.

## 1단계 — 작업 분할

1. CLAUDE.md "패키지 구조" 와 실제 소스 트리(Glob)를 보고, 기능 ID(requirements 4절)마다 손댈 파일·디렉터리를 정한다. 아직 없는 파일은 프레임워크 관례에 맞는 예정 경로로 적는다.
   - **먼저 기존 공통 코드를 찾는다** (CLAUDE.md "코드 구조 원칙"): "공용 코드 위치" 와 소스 트리에서 이번 기능에 쓸 수 있는 공통 모듈(에러 처리, 응답 형식, DB 접근, 검증, 유틸, 공통 컴포넌트)을 Grep · Glob 으로 찾는다. 있으면 새로 만들지 않고 계획서 "재사용할 기존 코드" 에 적는다.
   - 파일 구성은 코드 구조 원칙을 따른다: 여러 작업이 쓸 것은 공통 작업으로, 한 파일에 여러 책임을 몰지 않되 과분리하지 않는다. 판단 잣대는 "다른 팀원이 코드만 보고 이해할 수 있는가".
2. 기능을 작업으로 묶는다. 기준:
   - **작업끼리 담당 파일이 하나도 겹치지 않는다.** 디렉터리 단위로 적었으면 하위 파일까지 겹치지 않아야 한다.
   - 여러 기능이 같이 쓰는 파일(공통 설정, 라우터 등록, DI 설정, 공통 타입, 의존성 파일, 마이그레이션 순번 등)은 별도의 "공통 모듈" 작업으로 떼어 먼저 하도록 의존 관계를 건다.
   - 작업 하나는 에이전트 하나가 한 번에 끝낼 크기.
3. **작업 간 공통 약속**을 정한다: 뒤 작업이 앞 작업의 결과를 어떻게 쓰는지 (공통 모듈이 내보내는 함수·타입 이름과 시그니처, 기능 모듈이 내보내는 등록 함수 모양, 에러 형식 등). 동시에 일하는 작업들이 서로를 모른 채 맞물리려면 이 약속이 있어야 한다.
4. **겹침 검사**: 모든 작업 쌍의 파일 범위를 비교한다. 하나라도 겹치면 그 결과를 쓰지 말고 다시 나눈다. 다시 나눠도 안 되면 겹치는 파일과 이유를 적고 사용자에게 어떻게 할지 묻는다.
5. 의존 관계로 웨이브를 나눈다. 같은 웨이브의 작업은 동시에 실행된다. 한 웨이브의 작업 수가 동시 작업 수보다 많으면 그대로 두고 계획서에 적어 둔다 (`/run-wave` 가 나눠 띄운다).
6. 브랜치명은 `t<번호>-<짧은-영문-슬러그>` (소문자·숫자·하이픈만, 슬래시 금지 — Orca 가 worktree 이름을 그대로 브랜치명으로 쓴다).

## 2단계 — 계획서 `docs/tasks/plan.md`

```markdown
# 구현 계획서

- 근거 문서: <계약 문서 경로 3개와 각 상태(초안/확정)>
- 기준 브랜치: <기준> · 동시 작업 수: <n>
- 구현 체크리스트: [checklist.md](./checklist.md) · 계획 리뷰: [plan-review.md](./plan-review.md)

## 1. 목표와 범위

- 목표: <requirements "배경과 목표" 요약>

<모듈 구조와 나누는 방침 3~8줄. 기술 스택과 코드 구조 원칙은 CLAUDE.md 기준.>

### 작업 간 공통 약속

| 약속 | 정의 | 만드는 작업 | 쓰는 작업 |

## 3. 작업과 웨이브

| 작업 | 제목 | 기능 ID | 웨이브 | 의존 | 브랜치 | 카드 |

<웨이브별 동시 실행 묶음 설명. 동시 작업 수보다 많은 웨이브는 나눠 띄운다고 적는다.>

- 작업별 테스트 명령 형식: <CLAUDE.md 단일 테스트 명령 + 파일>
- 전체 확인: <마지막 웨이브 후 CLAUDE.md 전체 테스트 명령>

## 6. 위험과 대응

| 위험 | 영향 | 대응 |

## 7. 진행 방법

1. 계획 리뷰(`plan-review.md`)가 통과인지 확인한다. 블로커가 있으면 고치고 `/dev-pipeline:review-plan`.
2. `docs/` 를 기준 브랜치에 커밋한다 (worktree 는 커밋된 상태에서 만들어진다).

5. 웨이브의 작업이 모두 머지되면 다시 `/dev-pipeline:run-wave`.
```

## 3단계 — 구현 체크리스트 `docs/tasks/checklist.md`

계획서대로 따라 하면 구현이 끝나도록 작업마다 순서대로 적는다. 규칙:

- 항목 하나 = 확인 가능한 행동 하나 (파일 하나 만들기, 함수 하나 구현, 테스트 케이스 묶음 하나, 명령 하나 실행).
- 항목 ID 는 `T<번호>-<순번>`. 다른 문서(카드, 리뷰, 결과 기록)는 이 ID 로 항목을 가리킨다.
- 구현 항목에는 대상 파일과 근거(api-spec 엔드포인트, schema 테이블, 계획서 공통 약속)를 붙인다.
- 카드의 완료 조건마다 그것을 채우는 항목이 하나 이상 있어야 한다.
- 순서는 실제로 만들 순서다 (타입·공통 → 기능 → 테스트 → 검증).

```markdown
# 구현 체크리스트

작업마다 위에서부터 순서대로 진행한다. 이 파일은 계획 문서라 직접 체크하지 않는다. 항목별 결과는 작업마다 `results/T<번호>.md` 에 기록된다 (여러 작업이 동시에 같은 파일을 고치지 않도록).

## T1. <제목>

웨이브 1 · 브랜치 `t1-...` · 카드 [T1](./T1.md)

### 구현
- [ ] T1-1 `<경로>` — <무엇을 만든다>. 근거: <문서 위치>
- [ ] T1-2 ...

### 테스트
- [ ] T1-6 `<테스트 경로>` — <검증하는 경우: 정상, 대표 에러 경로>

### 검증
- [ ] T1-9 빌드: `<명령>`
- [ ] T1-10 이 작업의 테스트: `<명령>`
- [ ] T1-11 리뷰 블로커 0 (`/dev-pipeline:review-diff`)
```

## 4단계 — 작업 카드 `docs/tasks/T<번호>.md`

```markdown
# T<번호>. <제목>

- 기능 ID: F-xx, F-yy (공통 작업이면 "공통")
- 웨이브: <n>
- 의존: T<번호>, ... (없으면 "없음")
- 브랜치: `t<번호>-<슬러그>`
- 구현 순서: [checklist.md 의 T<번호>](./checklist.md#t<번호>) (항목 T<번호>-1 ~ T<번호>-<끝>)

## 담당 파일 범위

이 목록의 파일만 만들거나 고친다.

- `<경로>` — <무엇을 하는 파일인지 한 줄>

## 범위 밖

읽기만 하고 고치지 않는다. (있을 때만)

- `<경로>` (<소유 작업>)

## 지켜야 할 공통 약속

<계획서 "작업 간 공통 약속" 중 이 작업이 만들거나 쓰는 것>

## 완료 조건

- [ ] <계약 문서 기준의 동작> (근거: <문서 위치> · 체크리스트 <항목 ID>)
- [ ] 이 범위의 테스트 작성 (정상 + 대표 에러 경로)
- [ ] 빌드 성공: `<CLAUDE.md 빌드 명령>`
- [ ] 이 작업의 테스트 통과: `<CLAUDE.md 단일 테스트 명령 + 이 작업 테스트 파일>`
- [ ] 리뷰 블로커 0 (`/dev-pipeline:review-diff`)
```

## 5단계 — 계획 리뷰

세 문서를 다 쓰면 Skill 도구로 `dev-pipeline:review-plan` 을 실행한다. Skill 도구가 스킬 내용을 불러오지 못하면(비대화형 실행 등) `${CLAUDE_PLUGIN_ROOT}/skills/review-plan/SKILL.md` 를 Read 해서 그 절차대로 직접 실행한다. 0단계에서 계약이 초안인 채로 계속하기로 했으면 인자에 `--allow-draft` 를 준다. 리뷰 결과는 `docs/tasks/plan-review.md` 에 남는다.

블로커가 나오면 계획서·체크리스트·카드로 고칠 수 있는 것(파일 범위 겹침, 빠진 기능 배정, 의존 순서, 빠진 체크리스트 항목, 완료 조건)은 고치고 `review-plan` 을 한 번 더 실행한다. 계약 문서를 고쳐야 하는 블로커는 고치지 않고 보고한다 (계약 문서는 담당 에이전트가 사람 승인 후 고친다).

## 6단계 — 보고

- 만든 문서: 계획서, 체크리스트(작업별 항목 수), 카드 목록
- 웨이브 요약 표(작업 · 웨이브 · 의존 · 브랜치)와 겹침 검사 결과 (공유 파일을 어느 작업이 맡았는지)
- 계획 리뷰 판정과 남은 블로커 (고칠 곳 포함)
- 다음 단계: 리뷰가 통과했으면 계획서를 검토하고 `docs/` 를 커밋한 뒤 `/dev-pipeline:run-wave`. 블로커가 남았으면 고친 뒤 `/dev-pipeline:review-plan`. Orca 없이 직접 하려면 작업마다 `git worktree add ../<레포>-t<번호> -b <브랜치>` 후 그 worktree 에서 `/dev-pipeline:work-task T<번호>`.

## 7단계 — GitHub 이슈 (선택)

보고 뒤 AskUserQuestion 으로 "이 작업들을 GitHub 이슈로 만들까요?" 를 묻는다 (전부 / 일부 선택 / 만들지 않음). 비대화형이면 묻는 문장만 출력하고 멈춘다.

승인하면:

1. `gh auth status` 로 로그인 상태를, `gh repo view --json nameWithOwner` 로 대상 저장소를 확인해 보여준다. 실패하면 이유를 알리고 멈춘다.
2. 작업마다 `gh issue create --title "T<번호>. <제목>" --body-file <본문 파일>` 로 만든다. 본문은 카드 전문 + 체크리스트의 그 작업 섹션. 의존 작업은 의존 순서대로 만들고, 본문의 의존 표기는 이미 만든 이슈 번호로 바꿔 적는다.
3. 라벨·마일스톤·프로젝트 보드는 사용자가 지정할 때만 붙인다.
4. 만든 이슈 번호를 `docs/tasks/issues.md` 에 표(작업 · 이슈 번호 · URL)로 남기고 보고한다. 계획서에는 적지 않는다 — 리뷰 뒤 계획서가 바뀌면 `/run-wave` 가 계획 리뷰를 다시 요구하기 때문이다.
