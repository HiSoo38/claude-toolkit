# /plan-tasks — 병렬 작업 분할

추가 지시: $ARGUMENTS

## 0단계 — 사전 확인

1. 프로젝트 `CLAUDE.md` 를 읽는다. "기술 스택" 섹션이 없거나 값이 전부 `<!-- TODO -->` 면 **멈추고** "먼저 `/dev-pipeline:init-pipeline` 을 실행하세요" 라고 안내한다.
2. CLAUDE.md "계약 문서" 표에서 세 문서 경로를 읽는다 (없으면 `docs/requirements.md`, `docs/schema.*`, `docs/api-spec.md`).
3. 세 문서를 읽는다. 다음이면 경고하고 계속할지 묻는다:
   - 문서가 없거나 비어 있음
   - 상태가 "확정" 이 아님
   - "미정 사항" 에 체크 안 된 항목이 남아 있음

   (dev-pipeline 규칙: 계약 확정 전에는 기능 구현을 시작하지 않는다. 단 프로젝트 세팅·공통 모듈 작업은 계획해도 된다.)

## 1단계 — 작업 분할

1. CLAUDE.md "패키지 구조" 와 실제 소스 트리(Glob)를 보고, 기능 ID(requirements 4절)마다 손댈 파일·디렉터리를 정한다. 아직 없는 파일은 프레임워크 관례에 맞는 예정 경로로 적는다.
2. 기능을 작업으로 묶는다. 기준:
   - **작업끼리 담당 파일이 하나도 겹치지 않는다.** 디렉터리 단위로 적었으면 하위 파일까지 겹치지 않아야 한다.
   - 여러 기능이 같이 쓰는 파일(공통 설정, 라우터 등록, DI 설정, 공통 타입, 마이그레이션 디렉터리의 순번 등)은 별도의 "공통 모듈" 작업으로 떼어 먼저 하도록 의존 관계를 건다.
   - 작업 하나는 에이전트 하나가 한 번에 끝낼 크기.
3. **겹침 검사**: 모든 작업 쌍의 파일 범위를 비교한다. 하나라도 겹치면 그 결과를 보여주지 말고 다시 나눈다. 다시 나눠도 안 되면 겹치는 파일과 이유를 적고 사용자에게 어떻게 할지 묻는다.
4. 의존 관계로 단계(웨이브)를 나눈다. 같은 웨이브 안의 작업은 동시에 할 수 있다. 동시 작업은 2~3개를 권장한다.

## 2단계 — 출력

작업마다 아래 형식으로 출력한다.

```markdown
### T<번호>. <제목>
- 기능 ID: F-xx, F-yy
- 웨이브: <n> (의존: T<번호>, ... / 없음)
- 담당 파일 범위:
  - <경로>
- 범위 밖 (건드리면 안 되는 인접 파일): <경로> (있을 때만)
- 완료 조건:
  - [ ] <계약 문서 기준의 기능 동작> (근거: api-spec <엔드포인트>, schema <테이블/엔티티>)
  - [ ] 이 범위의 테스트 작성
  - [ ] 빌드 성공: `<CLAUDE.md 빌드 명령>`
  - [ ] 테스트 통과: `<CLAUDE.md 테스트 명령>`
  - [ ] `/dev-pipeline:review-diff` 블로커 0
- 권장 브랜치: `feat/t<번호>-<짧은-영문-슬러그>`
- worktree 예시: `git worktree add ../<레포이름>-t<번호> -b feat/t<번호>-<슬러그>`
- implementer 에게 줄 지시 예시: "T<번호> 작업을 해줘. 담당 파일 범위는 위 목록뿐이다."
```

마지막에 요약 표(작업 · 웨이브 · 의존 · 브랜치)와, Orca 에서 웨이브별로 worktree 를 만들어 implementer 에이전트를 실행하라는 안내를 붙인다. worktree 생성과 에이전트 실행은 이 커맨드가 하지 않는다.

## 3단계 — GitHub 이슈 (선택)

출력 뒤 AskUserQuestion 으로 "이 작업들을 GitHub 이슈로 만들까요?" 를 묻는다 (전부 / 일부 선택 / 만들지 않음). 비대화형이면 묻는 문장만 출력하고 멈춘다.

승인하면:

1. `gh auth status` 로 로그인 상태를, `gh repo view --json nameWithOwner` 로 대상 저장소를 확인해 보여준다. 실패하면 이유를 알리고 멈춘다.
2. 작업마다 `gh issue create --title "T<번호>. <제목>" --body-file <임시 파일>` 로 만든다. 본문은 2단계 출력 블록 그대로. 의존 작업은 이미 만든 이슈 번호로 바꿔 적는다(의존 순서대로 생성).
3. 라벨·마일스톤·프로젝트 보드는 사용자가 지정할 때만 붙인다.
4. 만든 이슈 번호와 URL 목록을 보고한다.
