## 코드 구조 원칙

코드 분리는 다른 목적을 위한 수단이 아니라 그 자체로 해야 하는 일이다. 한 파일이 길어지면 프로젝트 관리가 힘들어진다. 계획 · 구현 · 리뷰 모두 이 원칙을 기준으로 한다.

- **공통화**: 여러 곳에서 쓸 수 있는 것은 공통 모듈(컴포넌트 · 유틸 · 타입)로 뺀다. **이미 있으면 가져다 쓴다.** 새로 만들기 전에 위 "공용 코드 위치" 와 비슷한 이름의 기존 코드를 먼저 찾는다.
- **분리**: 분리할 수 있는 것은 분리한다. 발견한 시점에 처리하고 미루지 않는다. 단 자기 작업의 담당 파일 범위 안에서만 한다 (범위 밖이면 보고한다).
- **과분리 금지**: 너무 잘게 쪼개지 않는다. 관련된 것이 흩어지면 찾기 힘들고 파일을 타고타고 들어가야 한다.
- **판단 잣대는 인수인계**: 다른 팀원에게 넘겼을 때 코드만 봐도 이해되는가. 쪼갤지 합칠지 애매하면 이것으로 정한다.
- **기존 스타일 준수**: 주변 코드의 구조 · 이름 · 관용구를 먼저 보고 똑같이 맞춘다.
- **확장성**: 다음 기능이 같은 자리에 붙을 수 있게 만든다 (하드코딩된 분기 대신 등록 · 설정 방식 등).
- **점검과 보고**: 작업 끝에 분리 · 공통화를 점검하고 결과를 먼저 보고한다. 단 멀쩡히 돌아가는 기존 구조를 근거 없이 갈아엎지 않는다 — 겉모습이 바뀌는 변경은 계획에 있을 때만.

## 계약 문서 (docs/)

기능 구현은 아래 세 문서가 확정된 뒤에 시작한다. 순서는 requirements → schema → api-spec.

| 문서 | 경로 | 작성 에이전트 |
| --- | --- | --- |
| 요구사항 | `docs/requirements.md` | planner |
| 스키마 | <!-- TODO: docs/schema.sql 또는 docs/schema.md --> | db-designer |
| API 명세 | `docs/api-spec.md` | api-designer |

구현 계획(`docs/tasks/`)은 계약 문서가 아니다. `/dev-pipeline:plan-tasks` 가 계약 문서를 보고 계획서(`plan.md`), 구현 체크리스트(`checklist.md`), 작업 카드(`T<번호>.md`)를 만들고, `/dev-pipeline:review-plan` 이 리뷰해 `plan-review.md` 를 남긴다. 작업별 결과는 `results/T<번호>.md` 에 쌓인다.

규칙:

1. 구현 중 계약과 맞지 않는 부분을 발견하면 코드를 계약에 억지로 맞추거나 계약을 고치지 말고, 멈추고 보고한다.
2. 계약 변경은 사람이 승인한 뒤 해당 문서 담당 에이전트가 고친다.
3. 각 문서의 "미정 사항" 이 비어야 확정으로 본다.
